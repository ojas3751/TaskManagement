# ドキュメント一覧

タスク管理アプリの設計ドキュメント。

| 文書 | 役割 | 使う場面 |
| --- | --- | --- |
| [要件定義書](requirements.md) | **何を作るか、なぜその範囲か。** 目的・スコープ・利用シナリオ・非機能要件 | スコープの確認、方針の合意 |
| [機能仕様書](functional-spec.md) | **各機能の詳細と受け入れ条件** | 実装、動作確認 |
| [画面設計](design/ui.md) | ワイヤーフレーム（ボード画面、モーダル、エラー表示） | 画面の実装 |
| [画面モック](../mock/index.html) | HTML/CSS/JS の動くモック。バックエンド不要 | 配色・レイアウトの確認 |
| [データベース設計](design/database.md) | ER図、テーブル定義、`position` の採番方式 | DB構築、マイグレーション |
| [API設計](design/api.md) | エンドポイント一覧 | バックエンドの実装 |
| [開発計画](development-plan.md) | 実装の順序と完了の目安 | 進捗の管理 |
| [運用手順](operations.md) | システム構成、起動手順、バックアップ | 日常の利用、障害時 |

## 読む順

初めて読む場合は、上から順に読むと前提が積み上がる。

```
要件定義書 → 機能仕様書 → 画面設計 → データベース設計 → API設計
```

実装を進める際は [開発計画](development-plan.md) を起点にし、各 Step から関連する文書を参照する。

## 呼び方について

**利用者に見えるもの・本文書群の本文では「タスク」と呼ぶ。** DBのテーブル名とAPIのパスは `cards` のままとしている。意図的な使い分けであり、対応関係は [要件定義書](requirements.md) の「用語」に記載する。

## 版管理の方針

**各文書は独立した改訂履歴を持つ。** 設計だけが変わったときに要件定義書の版が上がると、「読み手が読み直す必要がある変更」という版の定義と食い違うため。

版を上げる基準は各文書の冒頭に記載する。

## 相互参照について

文書間のリンクは**ファイル単位**で張り、参照先の節名は本文中に明記する。見出しへのアンカーリンクは、見出しを変更したときに気づかないまま壊れるため使わない。
