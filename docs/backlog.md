### この文書の役割

**MVP 完成後にやることの候補を置く。** 探す場所を1つにするための文書であり、**決定の正本ではない。**

| 種類 | 正本 |
| --- | --- |
| **何を作るか**（F-xx の定義・MVP に入れない理由） | [要件定義書](requirements.md) 5.2 |

| **実装の順序** | [開発計画](development-plan.md) |

ここに書くのは、**上の文書には収まらないもの**（着手の優先順、複数機能をまたぐ方針、実装面の改善案、**仕様を変えるときに再検討すること**）に限る。

同じ内容を両方に書くと片方だけが古くなるため、**重なる部分はリンクで指す。**

> **3章と5章は性質が違う。** 3章（実装面の改善案）は**直せるならいつか直したいもの**。5章は**いまの仕様でよいと判断したもの**で、直すべき状態とは考えていない。**前提が変わったときに手段を思い出せるように**置いてある。

**着手するときは Issue を立てる。** この文書は候補の一覧であって、作業の管理はしない。

## 3. 実装面の改善案

**機能の追加ではなく、いまあるものの手直し。** F-xx の番号は振らない。

### ~~C-1. カード全体に `role="button"` と `tabIndex` が付いている可能性~~ **確認・対応済み**（2026-08-31、#95）

**確認した。懸念は当たっていたが、数は1つ多かった。** カード本体（`<article>`）に実際に付いていたもの。

```
role = button
tabindex = 0
aria-disabled = false
aria-roledescription = sortable
aria-describedby = DndDescribedBy-0
```

**Tab の停留点は3つではなく4つだった。**

| # | 要素 | 読み上げ名 |
| --- | --- | --- |
| 1 | チェックボックス | 「牛乳を買う」を完了にする |
| 2 | カード本体 | 牛乳を買う（ボタン、ソート可能） |
| 3 | タイトルのボタン | 牛乳を買う |
| 4 | ゴミ箱 | 「牛乳を買う」を削除 |

**この文書が「3つ」と書いていたのは、F-15 と F-22 でチェックボックスがどの列のタスクにも出るようになった分を数えていなかったため。** 20件の列なら 80 回。**2と3は読み上げ名まで同じ**で、同じ言葉を2回聞くことになっていた。

**対応は、タイトルのボタンを無くしてカード全体で受ける形。** 停留点は **3つ**になり、名前の重複も消えた。**キーは `Enter`（開く）と `Space`（掴む）で分けた。** 仕様の正本は [機能仕様書](functional-spec.md) 2.8 と [画面設計](design/ui.md) 2章。

> **専用のつまみ（ドラッグハンドル）を置く案は採らなかった。** この文書が警戒していたとおり**カード全体を掴める使い勝手を失う**うえ、**停留点も減らない。** `role="button"` だけを外す案も、`<article>` の意味は戻るが**停留点が減らない**ため採らなかった。

> **列（F-21）では同じ問題にならない。** 列も列全体を掴む形にしたので `<section>` に同じ属性が付くが、**増える停留点は列数ぶん（3〜10）で、中のタスクのように件数分は増えない。** 編集モード中はタスク側が inert なので、**モード中の停留点はむしろ減っている。**

### ~~C-2. `SortableContext` の並び替え戦略が使われていない~~ **対応済み**（2026-08-31、#93）

落ち先を線で示す方式にしたとき、`useSortable` が返す `transform` を当てるのをやめた（[画面設計](design/ui.md) 3章）。その結果 `verticalListSortingStrategy`（カードをずらす計算）は**計算されるが誰も使わない**状態になっている。

いま `SortableContext` が実際に担っているのは、**キーボード操作の移動先計算**と id の管理だけ。

**動作に害は無い。** ただし [`ListColumn`](../frontend/src/components/ListColumn.tsx) を読んだ人が「ここでカードが動く」と誤解する。**コメントを足すか、構成を整理するか**のどちらか。

> **コメントで片付けた。**（2026-08-31、#93）**構成は変えていない。** F-21 で列にも `SortableContext` を足したので、[`ListColumn`](../frontend/src/components/ListColumn.tsx) と [`BoardView`](../frontend/src/components/BoardView.tsx) の両方に「**実際に担っているのはキーボード操作の移動先計算と id の管理だけで、ずらす計算は使われない**」と書いた。**2つは役割が同じで向きが違うだけ**であることも、互いを指して書いてある。

### C-3. 応答待ちの間は盤面全体が操作できない

[`App`](../frontend/src/App.tsx) は「**飛んでいるリクエストは常に1本**」を前提に、失敗したら盤面ごと巻き戻す設計になっている。**ロックを外すとこの前提が崩れる**（控えているのが盤面全体なので、待っている間の操作まで巻き戻す。#43 で実際に不具合が出た）。

**いまは体感の問題になっていない。** 正常時の応答は 10ms 前後で、待機表示すら出ないため。

**着手するとしたら、困ってから。** タスクが増えるか、通信の遅い環境で使うようになったときに効いてくる。**設計の変更**であり、部分的な手直しでは済まない。

### C-4. ドラッグ&ドロップの自動テストが無い

落ち先を求めるロジック（[`dropTarget.ts`](../frontend/src/lib/dropTarget.ts) / [`moveCard.ts`](../frontend/src/lib/moveCard.ts)）にはテストがあるが、**掴んで落とす操作そのもの**は手動確認だけ。

**Step 11 で見つかった不具合は、すべて目視で見つかった。** 列の外に出られない／元の位置に戻る／2つ先と3つ先の間だけ挙動が違う／線が1px はみ出してスクロールバーが出る、のいずれも。

**積極的には勧めない。** ドラッグの自動テストは座標を伴うため費用対効果が悪い。**ただし「手動確認頼みである」ことは意識しておく。**

> **その後、同じことがキーボード操作でも起きた。**（2026-09-01、#93 / #97）**列の並び替えで3件、タスクの移動で5件**の不具合が、すべて**触ってみて初めて**見つかっている。掴んだものが下へ沈む／引き返すと1回目が空振りする／別の列で元の列の行数ぶん下がる／一番上に置けない／元いた列へ戻れない、など。
>
> **原因はどれも「矩形の形と位置」**で、**jsdom には配置が無い**（すべて 0 になる）ため、いまのテスト環境では**原理的に再現できない。** 落ち先を求めるロジックの単体テストは通っていた。
>
> **見つけたのは、症状を正確に言葉にした報告。** 「1回目だけ空振りする」「2件の列なのに4件の列の3番目に入る」といった具体的な言い方が、そのまま原因の切り分けになっていた。

### C-5. 例外が出ると画面が真っ白になる（`ErrorBoundary` が無い）

[`main.tsx`](../frontend/src/main.tsx) は `<StrictMode><App /></StrictMode>` だけで、**レンダリング中に例外が出ると React 19 はツリーごと外す。** `#root` が空になり、**何が起きたか分からない白い画面**が残る。

**次の C-6 と組で効く。** レスポンスの形が想定外だと描画中に落ちるので、片方だけ直しても足りない。

**直し方は既に画面の中にある。** 全面のエラー表示は [`LoadError`](../frontend/src/components/LoadError.tsx) が持っているので、`App` を囲むクラスコンポーネントを1つ足して、そこへ倒せばよい。

### C-6. API レスポンスを検証していない

[`board.ts`](../frontend/src/api/board.ts) の**10箇所すべてが `(await res.json()) as Board`**。型アサーションは実行時に何も確かめないので、**`res.ok` が true でも中身が `Board` である保証は無い。**

**「自前のバックエンド以外が答える」ことは実際に起きている。** 同じファイルのコメントが、開発中に Vite の proxy が 502 を返すことを認めている。**想定外の形が来ると `App` の `board.lists.flatMap(...)` で TypeError**になり、C-5 と重なって白画面になる。

**依存を増やさずにも塞げる。** `zod` などを入れなくても、`lists` が配列かを見る程度の型ガードを1つ置き、失敗を既存のエラー経路（`BoardApiError`）へ流すだけで、白画面は避けられる。

### C-7. `useCallback` が8個とも効いていない

[`App`](../frontend/src/App.tsx) の更新系ハンドラは、いずれも依存配列が `[state, isBusy]`。**`state` はボード全体なので、どんな更新でも全ハンドラが作り直される。** 参照の安定という `useCallback` の目的は果たされず、**コストだけ払って効果がゼロ**になっている。`React.memo` も無いため、`ListColumn` × 列数 × `TaskCard` × 件数がまるごと再描画される。

**依存に `state` が要ること自体は正しい。** 巻き戻し用の `before` をクロージャの外で取るためで、その判断は変えなくてよい。**足りないのは持ち方**で、`useReducer` に寄せる（ハンドラが `dispatch` にしか依存しなくなる）か、`state` を `useRef` に控えるかで解ける。

> **lint では見つからない。** `react/exhaustive-deps` は依存の**不足**を見るルールで、**過剰**は検出しない（実際 0 件だった）。`react-perf` の警告52件はこの症状の側だけを捉えている。

### C-8. モーダルからフォーカスが背後へ抜ける

4つのモーダルはいずれも `role="dialog"` と `aria-modal="true"` を付けているが、**`aria-modal` は支援技術へのヒントに過ぎず、DOM の他の要素を不活性にしない。** `Tab` を押すと**背後の盤面へフォーカスが移り、カードやボタンを操作できる。** 閉じた後に元の要素へ戻す処理も無い。

**`<dialog>` + `showModal()` にすると、フォーカストラップ・背景の不活性化・`Esc` が3つとも標準で付く。** 4ファイルに重複している `window` の keydown リスナと、それを避けるための `isModalOpen` フラグも要らなくなる。**このコードベースは既に `inert` を使いこなしている**ので、考え方としても地続き。

### C-9. `fetch` にキャンセルの口が無い

[`board.ts`](../frontend/src/api/board.ts) の `apiFetch` は `AbortSignal.timeout` を**内部で固定**しており、呼び出し側から `AbortSignal` を渡せない。そのため **全面エラーの「再読み込み」を連打すると、遅い応答が後着して古いボードで上書きしうる。** 応答待ちのロックは `pending` を触らない読み込み経路には効いていない。

**`AbortSignal.any([signal, AbortSignal.timeout(...)])` で合成し、`useEffect` のクリーンアップで `abort()` する**のが標準的な形。

### C-10. 入力欄のフォーカスが見えなくなる場面がある

詳細モーダルと `NameField` の入力欄が **`focus:outline-none` で輪郭を消し、border の色だけで代替**している。**Windows のハイコントラストモード（forced-colors）では border 色が上書きされるため、フォーカスが完全に見えなくなる。**

配色のコントラスト比をここまで検討している（[`index.css`](../frontend/src/index.css)）中で、ここだけが抜けている。`:focus-visible` の定義を1つ置くだけで済む。

**あわせて、エラー文言が入力欄と紐付いていない。** `role="alert"` は読み上げのきっかけにはなるが、`aria-invalid` と `aria-describedby` が無いので、**フォーカスを入力欄へ戻したときにエラー内容が読まれない。**

### C-11. `App.tsx` が836行で、責務が5種類同居している

読み込みの状態機械／8種類の API 呼び出しと楽観的更新／6個のモーダルの開閉／編集モードとキーボード処理／レイアウトが1つのコンポーネントに入っている。

**排他的なモーダルの状態を6個の `useState` で持っている**のも同じ問題の一部。同時に2つ真になってはいけない関係が型に現れておらず、**手で排他を保つコードとコメントが必要**になっている。`LoadState` を判別共用体で書けているので、同じ流儀をここにも当てればよい。

**React 19 の `useOptimistic` / `useTransition` は、この整理と一緒に効く。** 手書きのロールバックと「飛んでいるリクエストは1本」という前提（C-3）が、フレームワーク側の仕組みで置き換わる。

> **バックエンドには指摘なし。** JPA の落とし穴（N+1、`MultipleBagFetchException`、`cascade = ALL` が削除を打ち消す、一括 UPDATE と永続化コンテキスト）をいずれも踏んだうえで対処し、理由まで Javadoc に残せている。DTO の分離、`@RestControllerAdvice` への集約、`@Transactional(readOnly)`、Flyway ＋ `ddl-auto=validate` はすべて Spring Boot の定石どおり。

## 5. 仕様を変えるときに再検討すること

**いまの仕様のままでよいと判断したが、その判断が変わったら手段が要るもの。** 3章（実装面の改善案）と違い、**直すべき状態だとは考えていない。** 前提が変わったときに、ここを見れば「どう変えられるか」が分かるようにしておく。

**着手の候補ではない。** 仕様を変えると決めたときに初めて読む。

### S-1. 掴んでいる最中の `Esc` で、編集モードごと終了する

**いまの挙動。** 列を掴んでいる最中に `Esc` を押すと、**移動の取り消しと編集モードの終了が同時に起きる。**

**これでよいと判断した理由。**（2026-09-01、#101）**カーソルで掴んで操作すること自体には問題がない。** その状態で `Esc` を押す——つまり**メインの手段であるカーソル操作を、補助的なキー操作でキャンセルしなければならない状況**なら、**編集モードごと終了したほうがよい。**

**分けたくなったときの手段。** `Esc` を拾っているのが2か所あり、**両方が動いている**ために同時に起きている。

| 拾っている場所 | すること |
| --- | --- |
| dnd-kit（`KeyboardSensor`） | 移動を取り消す。**`preventDefault()` は呼ぶが、伝播は止めない** |
| [`App`](../frontend/src/App.tsx) | 編集モードを抜ける |

**`App` 側で「既に処理された `Esc`」を無視すれば分かれる。** dnd-kit が `preventDefault()` を呼んでいるので、**その印を見て、処理済みなら何もしない**だけでよい。**移動の取り消しだけが起き、モードは開いたまま**になる。

> **順序は問題にならない。** dnd-kit は `document` で、`App` は `window` で拾っており、**イベントは `document` → `window` の順に上がる**ので、`App` が見る時点では既に印が付いている。

**判断が変わる場面。** 列を1つ動かすたびにモードを開き直すことが煩わしくなったとき。**いまは列の並び替え自体が滅多に行わない操作**なので、その煩わしさが問題になっていない。
