## 2. 設計方針

### 2.1 再採番はトランザクションで完結させる

**再採番を伴う更新は1リクエスト・1トランザクションで完結させる。** 複数リクエストに分けると、途中で失敗した場合に並び順が壊れるため。

対象は `PATCH /api/lists/reorder`、`PATCH /api/cards/move`、**`POST /api/cards`** の3つ。いずれも「変更後の並び順すべて」をまとめて送る。

> **F-23（詳細モーダルからのリスト移動）に専用エンドポイントは作らない。** 「タスクを別リストの指定位置へ移す」という操作は F-13（ドラッグ&ドロップ）と同一であり、入力手段が違うだけ。分けると再採番のロジックが二重化し、片方だけ直して不整合を招く。

> **同じ理由で、後から増えた入力手段にも専用のエンドポイントを作っていない。**（2026-09-01 追記）
>
> | 機能 | 送り先 | 送る内容の違い |
> | --- | --- | --- |
> | **F-22**（ホバーでの完了操作） | `PATCH /api/cards/move` | 行き先が「完了列の先頭」に決まっているだけ |
> | **F-21**（列のドラッグ&ドロップ） | `PATCH /api/lists/reorder` | `[←] [→]`（F-05）と同じ。並べ終わった `list_ids` を丸ごと送る |
>
> **どちらもサーバーは1行も変えずに済んでいる。** 変わったのは「並びをどう求めるか」だけで、それは画面側の関心事。

### 2.2 初期表示は1リクエストで取得する

`GET /api/board` はボード・リスト・タスクをまとめて返す。リストごとにタスクを取得する作りにすると、リクエスト数が列数に比例して増える（N+1 問題）。

### 2.3 入力値の検証はサーバー側で必ず行う

画面側の入力制限は迂回できるため、**API は単独で呼ばれても不正なデータを受け付けない**ことを保証する。検証対象は以下。

| 対象 | 内容 |
| --- | --- |
| タイトル | 空文字でないこと、100文字以内 |
| 説明文 | 5,000文字以内 |
| リスト名 | 空文字でないこと、50文字以内 |
| 件数 | **追加したリスト10件以内**（`is_default` の3列は数えない）、1リストあたりタスク200件以内（`COUNT(*)` で判定） |
| リストの保護 | `is_default` が true のリストは改名・削除を拒否する |
| リストの位置 | **並び順の配列の末尾が `is_fixed_last` のリストであることを検査する。** 完了列自身を動かした場合も、他の列を完了より右へ動かした場合も、どちらも「末尾が完了列でない」という同じ状態になるため、これ1つで両方を弾ける（3.5） |

### 2.4 エラー応答

| 状況 | ステータス | 画面側の扱い |
| --- | --- | --- |
| 入力値が不正 | 400 ＋不正内容のメッセージ | 何が不正かを表示 |
| 対象が存在しない | 404 | 再読み込みを促す |
| 保護されたリストへの操作・件数上限超過 | 409 | 理由を表示 |
| DB に接続できない | **503** | 「Docker が起動しているか確認してください」 |
| サーバー自体が停止 | 応答なし（リクエスト失敗） | 「サーバーが起動していません」 |

エラー応答の本体は全て同じ形にする。

```json
{
  "code": "CARD_TITLE_TOO_LONG",
  "message": "タイトルは100文字以内で入力してください。",
  "field": "title"
}
```

| 項目 | 内容 |
| --- | --- |
| `code` | 画面側が分岐に使う識別子。メッセージの文言が変わっても壊れないようにするため |
| `message` | **そのまま画面に出せる日本語**。画面側で文言を組み立てない |
| `field` | 原因となった入力欄。該当しない場合は `null` |

Spring では `@RestControllerAdvice`（`GlobalExceptionHandler`）で一箇所に集約し、`MethodArgumentNotValidException`（Bean Validation）と自前の業務例外の両方をこの形に変換する。

#### エラーコード一覧

**これが正本。** 画面側は `code` で分岐するため、ここに無いコードを返してはならず、ここにあるコードを黙って変えてもいけない。

| `code` | ステータス | `field` | `message` |
| --- | --- | --- | --- |
| `CARD_TITLE_REQUIRED` | 400 | `title` | 入力してください。 |
| `CARD_TITLE_TOO_LONG` | 400 | `title` | タイトルは100文字以内で入力してください。 |
| `CARD_DESCRIPTION_TOO_LONG` | 400 | `description` | 説明文は5,000文字以内で入力してください。 |
| `LIST_TITLE_REQUIRED` | 400 | `title` | 入力してください。 |
| `LIST_TITLE_TOO_LONG` | 400 | `title` | リスト名は50文字以内で入力してください。 |
| `DUE_TIME_WITHOUT_DUE_DATE` | 400 | `due_at` | 期限の日付を入力してください。 |
| `CARD_IDS_REQUIRED` | 400 | `null` | 削除するタスクを選択してください |
| `CARD_IDS_MISMATCH` | 400 | `null` | 表示が最新ではありません。再読み込みしてください |
| `LIST_IDS_MISMATCH` | 400 | `null` | 表示が最新ではありません。再読み込みしてください |
| **`INVALID_REQUEST`** | 400 | 該当欄または `null` | 入力内容が正しくありません。 |
| `BOARD_NOT_FOUND` | 404 | `null` | ボードが見つかりません。再読み込みしてください |
| `LIST_NOT_FOUND` | 404 | `null` | リストが見つかりません。再読み込みしてください |
| `CARD_NOT_FOUND` | 404 | `null` | タスクが見つかりません。再読み込みしてください |
| `LIST_PROTECTED` | 409 | `null` | 最初からあるリストは名前の変更や削除ができません |
| `LIST_LIMIT_EXCEEDED` | 409 | `null` | 追加できるリストは10件までです |
| `CARD_LIMIT_EXCEEDED` | 409 | `null` | 1つのリストに置けるタスクは200件までです |
| `FIXED_LAST_MUST_BE_LAST` | 409 | `null` | 「完了」は常にいちばん右になります |
| **`DB_UNAVAILABLE`** | 503 | `null` | データベースに接続できません。Docker が起動しているか確認してください |
| **`INTERNAL_ERROR`** | 500 | `null` | エラーが発生しました。 |

> **`INVALID_REQUEST` は「表に載っていない検証違反」の受け皿。** ハンドラは「どのリクエストの、どの入力欄が、どの制約に違反したか」の対応表を持っており、そこに載っていない組み合わせはすべてこれになる。当てずっぽうのコードを返すと、画面側が黙って誤った分岐を通るため。
>
> **したがって `@NotNull` / `@NotEmpty` を足しただけでは、専用のコードは返らない。** 実際、`ReorderListsRequest` と `MoveCardRequest` の `@NotEmpty`、`CreateCardRequest` の `@NotNull id` などはすべてここに落ちる。専用のコードが要るなら、対応表に足すか、サービスから専用の例外を投げる（`CARD_IDS_REQUIRED` と `DUE_TIME_WITHOUT_DUE_DATE` が後者）。

> **`DB_UNAVAILABLE` は接続失敗とクエリ失敗を区別しない。** 画面側にできることは「DB を確認する」で同じであり、原因の切り分けはログを見る作業になるため。なお **DB が落ちているときに最初に起きるのはクエリの失敗ではなくトランザクションを開始できないこと**（`CannotCreateTransactionException`）で、これは `DataAccessException` を継承していない別系統の例外である。両方を捕まえないとここへ来ない。

画面側の挙動は [機能仕様書](../functional-spec.md) の「誤操作・エラーへの対策」を参照。

### 2.5 JSON の約束事

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| キーの命名 | **snake_case**（`due_at`, `has_due_time`, `is_default`） | DB の列名・本文書群の記述と一致させ、読み替えを不要にする。Spring 側は `spring.jackson.property-naming-strategy=SNAKE_CASE` で一括設定する |
| 文字コード | UTF-8 | |
| id | **文字列としての UUID**（`"3f1a…"`） | |
| 未入力の説明文 | **空文字 `""`**（`null` にしない） | DB 側も同様（[データベース設計](database.md)） |

### 2.6 日時の形式

**ISO 8601（オフセット付き）** でやり取りする。例: `"2026-08-20T09:00:00+09:00"`。Java 側は `OffsetDateTime`、DB 側は `timestamptz`。

| 状況 | `due_at` | `has_due_time` |
| --- | --- | --- |
| 期限なし | `null` | `false` |
| 日付のみ指定 | その日の **00:00**（`"2026-08-20T00:00:00+09:00"`） | `false` |
| 日時を指定 | 指定された時刻 | `true` |

> **`due_at` が 00:00 でも「時刻未指定」とは限らない。** 利用者が本当に 0 時を指定した場合と区別できないため `has_due_time` を別に持つ。**表示に時分を出すかどうかは `has_due_time` だけで決め、`due_at` の値から推測しない**（[データベース設計](database.md) の設計メモ）。

> **`spring.jackson.time-zone=Asia/Tokyo` を設定している。** 指定しないと Jackson は UTC に正規化し、`"2026-08-20T00:00:00Z"` の形で返す。値としては同じ瞬間だが、上の表が定めた `+09:00` の形と食い違う。

`created_at` / `updated_at` は API では返さない。MVP の画面で使わないため（DB には記録している）。

### 2.7 更新系は必ずボード全体を返す

**`GET /api/board` 以外のすべてのエンドポイントも、処理後のボード全体を同じ形で返す。**

| 判断 | 理由 |
| --- | --- |
| 差分ではなくボード全体を返す | 再採番を伴う操作では、**変更されるのは操作対象だけではない**（同じリストの全タスク、あるいは全リスト）。差分を返す設計にすると「どこまでが変わったか」を API と画面の両方で管理することになり、ズレたときに並び順が壊れる。全体を返せば画面は**受け取った内容で丸ごと置き換えるだけ**で済む |
| 転送量は問題にならない | 上限は全体で2,000件（[要件定義書](../requirements.md) の「データ量の想定上限」）。localhost 内の通信であり、性能目標に対して余裕がある |
| 例外を作らない | 一部だけ差分を返す作りにすると、画面側に2種類の更新経路ができる。**規模が小さいうちは経路を1本に保つ方が壊れにくい** |

## 3. 入出力仕様

以下、リクエスト本体・レスポンス本体はいずれも `application/json`。**成功時のレスポンスは 2.7 のとおり全て「ボード全体」**のため、3.1 で一度だけ示し、以降は繰り返さない。

### 3.1 `GET /api/board` — 一括取得（F-01）

リクエスト本体なし。

**レスポンス 200**（これが全エンドポイント共通の成功時レスポンス）

```json
{
  "id": "0a1b2c3d-0000-4000-8000-000000000001",
  "title": "マイタスク",
  "lists": [
    {
      "id": "00000000-0000-4000-8000-000000000101",
      "title": "TODO",
      "is_default": true,
      "is_fixed_last": false,
      "position": 0,
      "cards": [
        {
          "id": "0a1b2c3d-0000-4000-8000-000000000201",
          "title": "要件定義書を1.0にする",
          "description": "未決定事項をゼロにする。\n技術スタックの章を追加する。",
          "due_at": "2026-08-20T00:00:00+09:00",
          "has_due_time": false,
          "position": 0
        }
      ]
    },
    {
      "id": "00000000-0000-4000-8000-000000000103",
      "title": "完了",
      "is_default": true,
      "is_fixed_last": true,
      "position": 2,
      "cards": []
    }
  ]
}
```

- `lists` は `position` の昇順、各 `cards` も `position` の昇順で返す。**並べ替えは画面側で行わない**
- **完了列も全件返す。** 何件が画面に見えるか（F-25）は表示上の制御であり、取得件数を絞ると F-15（選択削除）の「すべて選択」が全件を対象にできなくなる

### 3.2 `POST /api/lists` — リストの追加（F-02）

```json
{
  "id": "00000000-0000-4000-8000-000000000104",
  "title": "設計"
}
```

- **`id` は画面側で採番して送る**（[データベース設計](database.md) の設計メモ）
- 挿入位置は指定しない。**サーバーが `is_fixed_last` のリストの左隣に入れ**、以降の `position` を振り直す
- レスポンス **201**

| エラー | ステータス | `code` |
| --- | --- | --- |
| 名前が空 | 400 | `LIST_TITLE_REQUIRED` |
| 名前が50文字超 | 400 | `LIST_TITLE_TOO_LONG` |
| `id` が無い | 400 | `INVALID_REQUEST`（`field` は `id`） |
| **`is_fixed_last` のリストが見つからない** | 404 | `LIST_NOT_FOUND` |
| 追加したリストが既に10件 | 409 | `LIST_LIMIT_EXCEEDED` |

> **404 は挿入位置の基準が無いときに返る。** 完了列は seed で必ず存在する前提なので、これが起きるのはデータの異常。

### 3.3 `PATCH /api/lists/{id}` — リスト名の変更（F-03）

```json
{ "title": "設計・調査" }
```

| エラー | ステータス | `code` |
| --- | --- | --- |
| 名前が空 / 50文字超 | 400 | `LIST_TITLE_REQUIRED` / `LIST_TITLE_TOO_LONG` |
| 対象が存在しない | 404 | `LIST_NOT_FOUND` |
| `is_default` が true | 409 | `LIST_PROTECTED` |

### 3.4 `DELETE /api/lists/{id}` — リストの削除（F-04）

リクエスト本体なし。内部のタスクも削除される（`ON DELETE CASCADE`）。削除後、残るリストの `position` を振り直す。**レスポンス 200**（ボード全体）。204 を返さないのは、変わるのが対象のリストだけではなく後続の `position` も詰まるため（2.7）。

| エラー | ステータス | `code` |
| --- | --- | --- |
| 対象が存在しない | 404 | `LIST_NOT_FOUND` |
| `is_default` が true | 409 | `LIST_PROTECTED` |

### 3.5 `PATCH /api/lists/reorder` — リストの並び替え（F-05, F-21）

**変更後の並び順すべて**を送る。配列の添字がそのまま `position` になる。

```json
{
  "list_ids": [
    "00000000-0000-4000-8000-000000000101",
    "00000000-0000-4000-8000-000000000104",
    "00000000-0000-4000-8000-000000000102",
    "00000000-0000-4000-8000-000000000103"
  ]
}
```

| エラー | ステータス | `code` |
| --- | --- | --- |
| 既存のリストと過不足がある（重複を含む） | 400 | `LIST_IDS_MISMATCH` |
| **`list_ids` が空** | 400 | `INVALID_REQUEST` |
| **`is_fixed_last` のリストが見つからない** | 404 | `LIST_NOT_FOUND` |
| `is_fixed_last` のリストが末尾にない | 409 | `FIXED_LAST_MUST_BE_LAST` |

> **配列が空のときに専用のコードは返らない。** `@NotEmpty` による違反はハンドラの対応表に載っていないため、汎用の `INVALID_REQUEST` になる（2.4 の注記）。画面側がここで文言を出し分ける必要は無いと判断しているため、専用のコードを起こしていない。

> **レスポンス 200**（ボード全体）。

> **「完了列は最右に固定」の検証はここに集約する。** 並び順を配列で受け取るため、**末尾の要素が `is_fixed_last` かどうかを見るだけ**で判定できる。移動元・移動先を個別に検査する必要はない。

### 3.6 `POST /api/cards` — タスクの追加（F-06）

```json
{
  "id": "0a1b2c3d-0000-4000-8000-000000000202",
  "list_id": "00000000-0000-4000-8000-000000000101",
  "title": "Flyway のマイグレーションを書く"
}
```

- **先頭に追加する。** サーバーが `position = 0` を振り、対象リストの既存タスクを +1 する（1トランザクション）
- 説明文と期限は追加時には受け取らない。追加直後は空／期限なしで、編集は `PATCH /api/cards/{id}` で行う
- レスポンス **201**

| エラー | ステータス | `code` |
| --- | --- | --- |
| タイトルが空 | 400 | `CARD_TITLE_REQUIRED` |
| タイトルが100文字超 | 400 | `CARD_TITLE_TOO_LONG` |
| `id` または `list_id` が無い | 400 | `INVALID_REQUEST`（`field` に欄名） |
| リストが存在しない | 404 | `LIST_NOT_FOUND` |
| そのリストが既に200件 | 409 | `CARD_LIMIT_EXCEEDED` |

### 3.7 `PATCH /api/cards/{id}` — タスクの編集（F-07, F-09）

**4項目すべてを毎回送る**（部分更新にしない）。詳細モーダルは4項目をまとめて保存するため、送る側・受ける側の両方が単純になる。

```json
{
  "title": "Flyway のマイグレーションを書く",
  "description": "V1 でテーブル作成、V2 で seed。\n一度適用したら編集しない。",
  "due_at": "2026-08-18T14:30:00+09:00",
  "has_due_time": true
}
```

- 期限を消す場合は `"due_at": null, "has_due_time": false`
- 説明文が未入力なら `""`（`null` を送らない）
- **`list_id` と `position` はここでは変更できない。** 移動は 3.9 の責務

| エラー | ステータス | `code` |
| --- | --- | --- |
| タイトルが空 / 100文字超 | 400 | `CARD_TITLE_REQUIRED` / `CARD_TITLE_TOO_LONG` |
| 説明文が5,000文字超 | 400 | `CARD_DESCRIPTION_TOO_LONG` |
| `description` が `null` | 400 | `INVALID_REQUEST`（`field` は `description`） |
| `due_at` が `null` なのに `has_due_time` が true | 400 | `DUE_TIME_WITHOUT_DUE_DATE` |
| 対象が存在しない | 404 | `CARD_NOT_FOUND` |

> **`due_at` と `has_due_time` の相関チェックはサービスが行う。** 2項目にまたがる検証で、ハンドラが持つ「入力欄名＋制約名」の対応表では表せないため（2.4）。

### 3.8 `DELETE /api/cards/{id}` — タスクの削除（F-08）

リクエスト本体なし。削除後、そのリストの `position` を振り直す（空番を残さない）。**レスポンス 200**（ボード全体）。3.4 と同じ理由で 204 にしない。

| エラー | ステータス | `code` |
| --- | --- | --- |
| 対象が存在しない | 404 | `CARD_NOT_FOUND` |

### 3.9 `PATCH /api/cards/move` — タスクの移動（F-13, F-23, F-22）

```json
{
  "card_id":      "0a1b2c3d-0000-4000-8000-000000000201",
  "from_list_id": "00000000-0000-4000-8000-000000000101",
  "to_list_id":   "00000000-0000-4000-8000-000000000102",
  "to_card_ids": [
    "0a1b2c3d-0000-4000-8000-000000000205",
    "0a1b2c3d-0000-4000-8000-000000000201",
    "0a1b2c3d-0000-4000-8000-000000000206"
  ]
}
```

| 項目 | 内容 |
| --- | --- |
| `to_card_ids` | **移動後の、移動先リストの並び順すべて。** `card_id` を必ず含む。配列の添字がそのまま `position` になる |
| 移動元リスト | **並びは送らない。** タスクが1件抜けるだけなので、サーバーが残りを詰めて振り直す |
| 同一リスト内の並び替え | `from_list_id` と `to_list_id` が同じ値になるだけで、他は変わらない |
| F-23（モーダルからの移動） | 移動先の**末尾**に付けた配列を送る。**F-13 と同じエンドポイント**（2.1 の方針） |

すべて1トランザクションで処理する。

| エラー | ステータス | `code` |
| --- | --- | --- |
| `to_card_ids` が移動後の状態と一致しない（重複を含む） | 400 | `CARD_IDS_MISMATCH` |
| **`from_list_id` が DB 上の所属と食い違う** | 400 | `CARD_IDS_MISMATCH` |
| **`to_card_ids` が空** | 400 | `INVALID_REQUEST` |
| タスクまたはリストが存在しない | 404 | `CARD_NOT_FOUND` / `LIST_NOT_FOUND` |
| 移動先が既に200件 | 409 | `CARD_LIMIT_EXCEEDED` |

> **`from_list_id` の食い違いも `CARD_IDS_MISMATCH` にする。** どちらも「画面が持っている情報が古い」という同じ原因（別のタブで動かした後など）で起き、画面側にできることも「再読み込み」で同じため、区別しない。そのまま進めると誤ったリストを詰め直してしまうので、素通りさせてはならない。

> **`from_list_id` と `to_list_id` が同じ（同一リスト内の並び替え）ときは、200件の上限を見ない。** 件数が増えないため。

### 3.10 `POST /api/cards/bulk-delete` — 選択削除（F-15）

```json
{
  "card_ids": [
    "0a1b2c3d-0000-4000-8000-000000000301",
    "0a1b2c3d-0000-4000-8000-000000000302"
  ]
}
```

1トランザクションで削除し、影響を受けたリストの `position` を振り直す。**レスポンス 200**（ボード全体）。

**同じ id が2回入っていても1件として扱う。** 画面がそう送ることは無いが、送られても件数の突き合わせが狂わないようにするため。

| エラー | ステータス | `code` |
| --- | --- | --- |
| 配列が空、または `card_ids` が無い | 400 | `CARD_IDS_REQUIRED` |
| いずれかが存在しない | 404 | `CARD_NOT_FOUND` |

> **ここは `@NotEmpty` を使わずサービスが判定している。** 付けると 2.4 の注記のとおり汎用の `INVALID_REQUEST` になり、この表が定めた `CARD_IDS_REQUIRED` を返せなくなるため。**「専用のコードが要るならサービスが投げる」**という方針で、`DUE_TIME_WITHOUT_DUE_DATE` と揃えてある。

> **存在しない id が混ざっていたら、1件も削除せずに 404 を返す。** 「消せたものだけ消す」と、画面に出ていた選択と実際に消えたものがズレたまま処理が終わる。まとめて失敗させ、再読み込みさせる方が状態を追いやすい。
