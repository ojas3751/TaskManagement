## 3. 順序の根拠

| 判断 | 理由 |
| --- | --- |
| **Step 1（DB構築）を先頭に置く** | DB とバックエンドが土台であり、後から差し込むと画面側の作り直しが発生する |
| **「永続化」の独立した Step を設けない** | DB を先に作る構成では、Step 1〜3 の時点で最初から永続化された状態になる。LocalStorage 方式のときは独立した Step が必要だった |
| **Step 8 で実用ラインに到達させる** | タスクの追加・編集・削除・移動が揃えば、自分の実データを入れて使い始められる。使い始めると開発が続きやすい。**移動手段がモーダル経由だけでも、この条件は満たせる** |
| **移動の「難しさ」を2つに分けて順に片付ける** | タスクの移動には、**`position` の再採番というデータ側の難しさ**と、**ドラッグ&ドロップという UI 側の難しさ**がある。Step 8 で F-23 を作れば、入力手段が選択欄だけなので**データ側の難しさに集中できる**。両方を同時にデバッグせずに済む |
| **ドラッグ&ドロップを最後に回す** | 最も実装が難しいため。Step 8 で再採番と移動APIが完成していれば、**Step 11 は同じ処理を呼ぶ入力手段を1つ足すだけ**になる |
| **移動ボタン（F-12）を作らない** | 完成版に残さないと分かっているものを作らない。作って消す手間に加え、**その期間だけ正しい文書を書き、後で書き直す手間**も発生する（実際 v0.8 では画面設計に段階別の図を2つ持っていた） |

## 4. Step ごとの補足

| Step | 補足 |
| --- | --- |
| 0 | **Java ファイルは書かない。** Spring Initializr が生成する骨組みのままにし、Gradle の設定も最低限に留める。ただし**依存関係は先に全部入れておく**（Web / Data JPA / Validation / Flyway / PostgreSQL Driver）。後から足すより手戻りが少ない |
| 0〜1 | **完了時点で、起動手順を [運用手順](operations.md) に記載すること**（UC-01）。※ v1.3 時点で先に記載済み。実際に動かして食い違いがあれば直す |
| 1 | Flyway のマイグレーションファイルは**一度適用したら編集しない**（チェックサムが記録されるため）。詳細は [データベース設計](design/database.md) の「スキーマの管理」 |
| 2 | **`GET /api/board` で N+1 を踏んでいないか、発行 SQL のログで必ず確認する。** JPA では黙っていると必ず踏む |
| 6 | 色コードはここで確定する。純粋な赤に白文字ではコントラスト比 4.5:1 を満たさないため、実測が必要 |
| 7 | 通信エラーの確認には、意図的に停止する必要がある。E-03 は `bootRun` を `Ctrl + C`、E-04 は `Stop-Service postgresql*`（確認後に `Start-Service` で戻す） |
| 8 | `position` の再採番は [データベース設計](design/database.md) の「position の採番方式」に従う。**F-23 の移動先は末尾**のため、位置指定の実装は Step 11 まで不要 |
| 10 | 「10件目が上部だけ覗く」高さは、実際にタスクを並べないと決められない |
| 11 | **F-23 は残す。** ドラッグ&ドロップはマウスを専有する操作であり、F-23 がキーボードだけで移動できる唯一の手段になる |
| ~~任意~~ | ~~タスクの削除ボタンの出し方を決める~~ **決定済み**（2026-08-15、ゴミ箱アイコンを期限と同じ行の右端に常時表示）。[要件定義書](requirements.md) の「決定事項の記録」を参照 |

## 5. ブランチ運用

**都度ブランチを切る運用はしない。** 学習段階では分岐が増えすぎて把握しづらくなるため、原則 `main` に直接コミットする。

以下の場面では、必要に応じてブランチを切る。

| 場面 | 理由 |
| --- | --- |
| Step 11（ドラッグ&ドロップ） | 最難関で、失敗したら丸ごと捨てたくなる可能性がある。**ただし F-23 が残るため、失敗しても操作不能にはならない。** 丸ごと捨てても Step 10 の状態で使い続けられる |
| ~~技術スタックの選び直し~~ | **該当しなくなった。** 2026-08-16 に技術スタックが確定したため（[要件定義書](requirements.md) の「技術スタック」） |
| 動いている状態を壊す変更 | Step 8 以降は実用できる状態のため、壊さずに試したい場面が出てくる |
