## 1. リスト（列）の仕様

### 1.1 デフォルトの3列

初回起動時（seed 投入時）、以下の3列が用意される。

| 列名 | 削除 | 名前変更 | 並び替え |
| --- | --- | --- | --- |
| TODO | 不可 | 不可 | 可 |
| 進行中 | 不可 | 不可 | 可 |
| **完了** | 不可 | 不可 | **不可（常に最右に固定）** |

削除・改名は、UI 上ボタン自体を表示しない。保護の根拠は `lists.is_default` フラグであり、**アプリケーション層で担保する**（DBの制約では表現しにくいため）。

### 1.2 ユーザーが追加した列

- 追加・名前変更・削除がすべて可能
- 削除時は確認ダイアログを出し、中のタスクも一緒に削除される（DB上は `ON DELETE CASCADE`）
- **新規追加した列は「完了」の左隣に挿入される**

### 1.3 列の並び替え

タスクの流れは「完了より手前の工程が増える」ことが多いため、列の順番を後から変更できるようにする。

- 「完了」を除く全ての列を、左右に並び替えできる
- 「完了」より右へは移動できない（`lists.is_fixed_last` で表現する）

並び替えの操作は **`[← →]` ボタンとドラッグ&ドロップ（F-21）の2つ**で行う。**どちらも 1.6 の編集モードの中にある。**

> **`[← →]` ボタンは残す。** ドラッグ&ドロップはマウスを専有する操作であり、これだけにすると**キーボードで列を動かせなくなる。** タスクの移動で F-23 を残したのと同じ考え方。
>
> ~~並び替えの操作は「← →」ボタンで行う。列のドラッグ&ドロップは MVP に含めず、F-21 として後から追加する。~~ ~~**列の `[← →]` ボタンは残す。** タスクには移動ボタンを設けない（F-12 は欠番）が、列については代替手段（F-21）が MVP に入っていないため、廃止すると並び替える手段がなくなる。また列見出しは1列につき1つしかなく、タスクのように件数分並ぶわけではないので、閲覧性への影響も小さい。~~
>
> **上の記述は失効した。**（2026-08-31、#89）F-21 を実装し、**両方をモードの中に置く**ことにしたため。「列見出しは1列に1つなので閲覧性への影響も小さい」という見立ても**取り下げる** — 実物では**矢印のために列の最上部に1行を常設しており**、その1行は 1.6 で撤去する。

### 1.4 「完了」列の特別扱い

| 項目 | 仕様 |
| --- | --- |
| 選択削除 | 各タスクにチェックボックス。**普段はカードの下に隠れており、ホバーまたはフォーカスで現れる**（[画面設計](design/ui.md) 1章）。`[〇件を削除]` でまとめて削除（確認ダイアログあり） |
| 全選択 | `[全選択]` を用意し、これで全件削除を代替する。**スクロールで見えていないタスクも対象にする** |
| 選択の行 | `[全選択] [選択解除] [〇件を削除]` を1行にまとめ、**「完了」列に常時表示する**（#20）。**1件も選んでいない間は `[選択解除]` と `[0件を削除]` を押せない状態にする。** タスクが0件の列では `[全選択]` も押せない |
| **タスクの移動** | **他の列と同じ手段で移動できる。** ドラッグ&ドロップ（F-13）と詳細モーダル（F-23）の両方が使え、**どちらでも完了の左隣へ差し戻せること**（UC-03）が必須 |

チェックボックスは **どの列のタスクにも出す**（F-22）。**出し方は同じで、意味だけが違う** — 「完了」列では**選択**、それ以外の列では**「完了にする」**（3.4）。

> **完了列のタスクは削除しない限り蓄積し続ける。** 自動削除や保持期間の仕組みは持たない（[要件定義書](requirements.md) の UC-04 を参照）。この選択削除が、完了列の件数を**まとめて**減らす手段である。**1件ずつなら F-08（カード上のゴミ箱アイコン）でも消せる** — ゴミ箱は完了列のタスクにも出る。

> **選択状態は DB に保存しない。** 画面上の一時的な状態であり、テーブルに持たせると再読み込み時の初期化責務が発生するため。

> **表示件数の制限は持たない。**（2026-08-29、#64）以前は「9件まで表示し、10件目が上部だけ覗く。『もっと見る』で全件展開」という仕様（F-14）を置いていたが、**取り下げた。** 完了列が伸びても他の列を押し流さないのは 1.5（F-25）が全列に対して保証するため、完了列だけの特別扱いとして持つ理由が無くなった。経緯は [要件定義書](requirements.md) の「機能一覧」を参照。

### 1.5 列の高さとスクロール（F-25）

| 項目 | 仕様 |
| --- | --- |
| 盤面の高さ | **ウィンドウの高さに収める。** ページ全体が縦にスクロールすることはない |
| 列の高さ | 収まる範囲で中身なりの高さになる。**入りきらない列は、その列の中だけがスクロールする** |
| スクロールする範囲 | **タスク一覧の領域だけ。** 並び替えの矢印・リスト名・`[+ タスク追加]` はスクロール領域の**外**に置く |
| 表示件数の上限 | **設けない。** 見える件数はウィンドウの高さ次第 |
| 適用範囲 | **全列。** 完了列も他の列も同じ扱い |

> **なぜスクロールを列の中に閉じるのか。** ページ全体がスクロールすると、ボード名もリスト名も一緒に流れて隠れる。**列が多いボードでは、どの列に入れようとしているかが分からなくなる。** スクロールする範囲をタスク一覧だけに絞れば、見出しは常に見えたままになる。

> **見出しを貼り付ける（`position: sticky`）方法は採らない。** 見出しをスクロール領域の外の兄弟要素として置けば、貼り付ける必要がそもそも無い。

> **表示件数に上限を設けない。** 「最大9件分の高さ」とする案もあったが、**「1行のカード9件ぶん」という根拠の書けない定数**が残る。さらにタスクのタイトルは折り返すため（最大100文字）、同じ高さでも実際に見える件数はぶれる。**「9件」が保証にならない数字を仕様に置くことになる。**

### 1.6 リストの編集モード（F-24 ＋ F-21）

**リストに関する操作は、すべてこのモードの中で行う。** モード外の盤面に出るのは**リスト名とタスクだけ**になる。

#### 出入りの仕方

| 項目 | 仕様 |
| --- | --- |
| 入口 | **ボードの見出しの横**に `[ リストを編集する ]` を置く。押すとモードに入る |
| 出口 | 同じボタンをもう一度押す。**`Esc` でも抜ける** |
| モード中であること | ボタンの見た目で示し、**支援技術にも伝える**（`role="status"`） |

#### モードの内と外

| | モード外 | モード中 |
| --- | --- | --- |
| 列の見出し | **リスト名だけ** | リスト名 ＋ `[←] [→]` ＋ 編集アイコン |
| 列の並び替え（F-05 / F-21） | できない | **ドラッグ&ドロップと `[←] [→]` の両方** |
| 列の改名・削除（F-03 / F-04） | できない | 編集アイコンから「リストの詳細モーダル」 |
| 列の追加（F-02） | **`[+ リスト追加]` を出さない** | 盤面の右端に出す |
| タスクの操作 | すべてできる | **すべて止める** |

> **モード中はタスク側の操作をすべて止める。** 列を掴む操作は**列全体を掴む**形になるが、その内側にはカードのドラッグ（F-13）・ホバーのチェック（F-22）・選択（F-15）・`[+ タスク追加]`・タスクのゴミ箱（F-08）が載っており、**押したいのがどちらなのかが決まらない。**

> **`[+ リスト追加]` もモードの中に入れる。** これだけ外に残すと「リストへの操作はモードの中」という原則に例外が1つできる。**デフォルトの3列は必ず存在する**ので、行き止まりにはならない。

#### 列の並び替えの見せ方

| 項目 | 仕様 |
| --- | --- |
| 掴む範囲 | **列全体。** 専用のつまみは置かない（モード中はタスク側が止まっているため競合しない） |
| 落ち先の表示 | **縦の線。** 落ちる位置に線を引き、他の列は動かさない |
| キーボード | 列にフォーカスして `Space` で掴み、`←` `→` で動かし、もう一度 `Space` で置く |
| `[←] [→]` | 列見出しの行に置く。**端の列では押せない状態にする**（「完了」より右へは行けない） |
| 「完了」列 | **動かせない。** 掴めず、`[←] [→]` も出さない |

> **線にする理由は F-13 と同じ**（3.2）。**盤面の中で落ち先の見せ方を1つに揃える。**

> **列の最上部にあった「並び替えの行」は撤去する。** いまは矢印を常設するために `h-5` の行を全列に置いており、**「完了」列にはボタンを出さないが高さだけ空ける**扱いをしていた（[画面設計](design/ui.md) v1.6）。**常設をやめれば、その理由ごと消える。** 矢印は列見出しの行に移す。

#### 送信

**サーバーは変更しない。** 並び替えの結果は、`[←] [→]` でもドラッグ&ドロップでも**同じ `PATCH /api/lists/reorder`**（[API設計](design/api.md) 3.5）へ、並べ終わった `list_ids` を丸ごと送る。**入力手段が違うだけで、送るものは同じ。**

## 2. タスクの仕様

### 2.1 持たせる情報

| 項目 | 必須 | 内容 |
| --- | --- | --- |
| タイトル | 必須 | タスク名。空文字は不可 |
| 説明文（メモ） | 任意 | 詳細ポップアップで閲覧・編集。一覧には表示しない |
| 期限 | 任意 | 年月日は必須、時分は任意（2.4 参照） |
| 作成日時 | 自動 | 自動で記録 |

### 2.2 リスト内でのタスクの表示

一覧に表示するのは **タイトル と 期限** の2つのみ。説明文は表示しない。

**操作要素は削除のゴミ箱アイコン1つだけとし、期限と同じ行の右端に置く。**

| 項目 | 仕様 |
| --- | --- |
| 削除の見せ方 | **ゴミ箱のアイコン。** 「削除」の文字ボタンは使わない |
| 配置 | **期限と同じ行の右端。** 削除のためだけに行を増やさない |
| 表示条件 | **常時表示。** ホバー時のみにはしない |
| 期限がない場合 | 行は残し、ゴミ箱だけを右端に置く。**行の高さは期限がある場合と揃える** |
| 色 | **タスクの文字色に追従させる。** 期限超過・当日（白文字）でも完了列（黒文字）でも判別できること |

> **ホバー時のみにしない理由。** 常時表示の圧迫感を避けるのが目的だったが、**アイコン化と行の共有で高さの問題は解消した**。ホバーでしか現れない操作は、その要素にマウスを乗せるまで存在に気づけない。利用者が1名（P-1）で習熟が前提とはいえ、隠す利得が小さい。
>
> **アイコンは画像ファイルや絵文字ではなく、実装側の図形描画で作る。** 絵文字（🗑）はフォントによって字形も色も変わり、文字色への追従もできない。
>
> **行の高さを揃える必要がある。** 期限の有無でタスクの高さが2種類できると、縦に並べたときに視線の間隔がばらつく。

### 2.3 タスクの追加位置

**「+ タスク追加」はリストの最上部に置き、追加したタスクはそのすぐ下（＝リストの先頭）に入る。**

| 項目 | 仕様 |
| --- | --- |
| 追加ボタンの位置 | リストの**最上部**。列見出しの直下 |
| **出す列** | **「完了」列以外のすべて**（#20）。完了列には出さず、同じ位置に選択の行（1.4）が入る。完了へタスクを入れるにはドラッグ&ドロップ（F-13）か詳細モーダル（F-23）を使う |
| 新規タスクの挿入位置 | **リストの先頭**（`position` の最小） |

> **末尾ではなく先頭に入れる理由。** 追加ボタンが最上部にあるのに追加物が末尾に現れると、**追加したものが視界の外に出る**。**タスクが入りきらない列ではスクロールしないと確認できず**、「登録できたのか」が分からない。操作した位置と結果が現れる位置を一致させる。
>
> **`position` の採番に影響する。** 末尾追加は「`max(position) + 1` を振るだけ、再採番なし」で済んだが、**先頭追加はそのリストの全タスクの再採番を伴う**。詳細は [データベース設計](design/database.md) の「position の採番方式」を参照。

### 2.4 期限の入力ルール

- 期限を設定する場合、**年月日は必須**
- **時分は任意**。入力しなくてもよい
- 時分が入力されなかった場合、内部的には **00:00** として扱う
- 時分を指定するかどうかは、**「時刻を指定する」チェックボックス**で切り替える（[画面設計](design/ui.md) の「タスクの詳細モーダル」を参照）。オフのときは時分の入力欄を無効にする。この状態が `cards.has_due_time = false` に対応する

> 入力欄の初期値を 00:00 にするだけでは、「未入力」と「0時を指定した」を利用者が区別できない。チェックボックスで明示的に切り替えることで、`has_due_time` の意味が画面上でも一貫する。

### 2.5 期限の表示ルール

**月・日・時・分はいずれも2桁でゼロ埋めする。** 桁数が揃うことで、タスクが縦に並んだときに日付の位置が視覚的に揃う。

| 条件 | 表示 |
| --- | --- |
| 時分が未入力 | 時分を表示しない（例: `08/20`, `01/05`） |
| 時分が入力済み | 時分まで表示（例: `08/20 15:00`, `08/20 09:05`） |
| 期限の年が今年と異なる | 年を表示（例: `2027/01/05`） |
| 期限の年が今年と同じ | 年を表示しない（例: `08/20`） |
| 期限が未設定 | 何も表示しない |

年は4桁のまま表示する（ゼロ埋めの対象外）。

### 2.6 期限による色分け

色は **太めの色付きボーダーでタスクを囲う**ことで表現する。

| 期限までの残り | ボーダー | 背景 | 文字色 |
| --- | --- | --- | --- |
| 期限超過 | 太い赤 | **赤** | **白** |
| 当日 | 太い赤 | **赤** | **白** |
| 翌日 | 太い赤 | 通常 | 通常 |
| 2〜3日以内 | 太い黄 | 通常 | 通常 |
| 4日以降 / 期限なし | 通常 | 通常 | 通常 |

背景が赤になるのは「当日および期限超過」のみ。その場合、コントラスト確保のため文字色を白にする。

**色コードは Step 6 で確定した。**

| 区分 | ボーダー | 背景 | 文字 |
| --- | --- | --- | --- |
| 期限超過・当日 | 3px `#b3261e` | `#b3261e` | `#ffffff`（6.5:1） |
| 翌日 | 3px `#b3261e` | 通常 | 通常 |
| 2〜3日以内 | 3px `#ffca61` | 通常 | 通常 |
| 4日以降・期限なし | 1px `#172b4d` | 通常 | 通常 |

**ボーダーの太さが変わってもカードの大きさは変えない。** 細くなるぶん内側の余白を増やして相殺する。並んだカードの幅や高さがずれると、色分け以前に一覧として読みにくくなるため。

> **黄は「二重線」から「明るい一重」に変わった。**（2026-08-25 決定）
>
> 当初は「明るい黄のボーダー＋内側に濃い縁1本」の二重線としていた。黄は輝度が高く、明るくするほど白背景との差が消えるため（`#FFFB00` で **1.07:1**）、輪郭の識別を内側の濃い縁に担わせる設計だった。
>
> **実物を見て取りやめた。** 1px の内側の縁は黒っぽい線にしか見えず、外側の明るい黄はうるさいだけで、二層に分けた意味が視覚的に成立していなかった。
>
> **一重にすると、今度は 3:1 と明るさが両立しなくなった。** 3:1 を満たす最も明るい黄は `#c78500`（3.10:1）程度で、暗い黄土色にしかならない。それでは「期限が近いことに気づかせる」という目的を果たせない。
>
> **そこで 3:1 を外し、明るい黄 `#ffca61` を採った。** 期限はカード上に「08/28」と文字でも出ており、色は唯一の伝達手段ではないため。詳しい根拠は [要件定義書](requirements.md) の「ユーザビリティ・アクセシビリティ」の但し書きを参照。

> **黄・オレンジを濃くすると、目立たなくなる。** 濃くしても赤との区別は付く。問題は区別ではなく**目立ち方**で、輝度が赤に近づいた濃いオレンジは周囲に沈み、**「期限が迫っている」ことを際立たせる働きをしなくなる。** 色分けの目的は区別することではなく気づかせることなので、明るい側を選んだ。

> **4日以降・期限なしのカードにも輪郭線を引く。** 当初は透明（枠なし）としていたが、輪郭が無いと「色が付いていない」ことが状態として読めない。細い線を引くことで、**細い無彩色の線 → 太い色付きの線**という対比が生まれ、色の有無が状態として伝わる。

**判定は「時刻」単位で行う。** 現在日時と期限日時を比較し、期限日時を過ぎていれば「期限超過」とする。時分が未入力のタスクは 00:00 として扱われるため当日中は常に「期限超過」と判定されるが、表示は「当日」と同一のため見た目の差は出ない。

### 2.7 「完了」列での上書き

「完了」列にあるタスクは、期限に関わらず以下の見た目に統一する（終わったタスクを警告する意味がないため）。

| ボーダー | 背景 | 文字色 |
| --- | --- | --- |
| 薄いグレー | 薄いグレー | 黒 |

**この上書きは「完了」列に在ることだけを条件とする。** したがって差し戻し（UC-03）で他の列へ移すと、期限による色分けが復活する。

### 2.8 タスクの詳細表示

タスクをクリックすると **ポップアップ（モーダル）** が開く。

- 説明文が長くても読みやすいよう、十分な幅と高さを確保する
- ポップアップ内でタイトル・説明文・期限を編集して保存できる
- 背景クリックまたは閉じるボタンで閉じる
- **説明文の改行は、入力どおりに表示へ反映される**（`white-space: pre-wrap` 相当）

> 改行を保持する実装で `innerHTML` を用いると XSS の入口になる。説明文は**必ずエスケープして表示する**（[要件定義書](requirements.md) の「セキュリティ」を参照）。

### 2.9 入力欄の文字数制限

タイトル・説明文・リスト名の入力欄には、**現在の文字数と上限を常に表示する**。

| 項目 | 上限 | 表示例 |
| --- | --- | --- |
| タスクのタイトル | 100 | `12/100` |
| タスクの説明文 | 5,000 | `348/5000` |
| リスト名 | 50 | `4/50` |

- 表示位置は入力欄の**右下**
- **上限に達したら、それ以上入力できない**（入力を止める）
- 上限に達している間は、**文字数の表示を赤色にする**

> **赤色の文字もコントラスト比 4.5:1 以上を満たすこと。** 背景が白の場合、`#FF0000` は基準を満たさないため、暗めの赤を使う。

#### 実装上の注意

| 注意点 | 内容 |
| --- | --- |
| 貼り付け | 上限を超える文字列を貼り付けた場合、**上限までで切り詰める**。貼り付け自体を拒否しない |
| 文字数の数え方 | **絵文字や一部の漢字は、プログラム上2文字として数えられる場合がある**（UTF-16 のサロゲートペア）。見た目の文字数と一致させるには、書記素単位で数える必要がある。MVP では単純な文字数カウントで可とし、この差異を許容する |
| サーバー側の検証 | **入力欄で止めていても、サーバー側で必ず再検証する。** APIは直接呼び出せるため、画面側の制限は迂回できる |

## 3. タスクの移動・並び替え

### 3.1 手段は2つ。どちらも恒久機能

| 手段 | ID | 内容 |
| --- | --- | --- |
| **ドラッグ&ドロップ** | F-13 | 別の列へ、また列内の任意の位置へ移動する。**主たる手段** |
| **詳細モーダルからのリスト移動** | F-23 | タスクを開き、リストの選択欄で移動先を選ぶ。**列は選べるが、列内の位置は選べない** |

これに加えて、**行き先が「完了」列に決まっている場合だけの近道**がある（3.4）。汎用の移動手段ではないので、上の2つには数えない。

**移動ボタン `[↑][↓][←][→]` は作らない**（F-12 は欠番）。ボタンと `[削除]` が全タスクに常時並ぶと、1件あたりの高さと情報量が増え、**ボードを俯瞰したときの閲覧性が損なわれる**ため。タスク管理ツールにおいて「一覧して状況を把握する」ことは「操作する」ことと同等以上に重要であり、それを削ってまで操作手段を増やすのは割に合わない。画面モックで実物を確認したうえでの判断（[要件定義書](requirements.md) の「機能一覧」の注記を参照）。

> **F-23 は F-13 の劣化版ではない。** ドラッグ&ドロップは**マウスを専有する操作**であり、キーボードだけでは実行できない。F-13 が唯一の移動手段だと、[要件定義書](requirements.md) の「ユーザビリティ・アクセシビリティ」にある「ポインタ操作以外の移動手段」の要件を満たせない。**F-23 は両方が完成した後も残す。**

### 3.2 ドラッグ&ドロップ（F-13）

| 項目 | 仕様 |
| --- | --- |
| 掴む対象 | タスク1件 |
| 落とせる先 | 任意の列の、任意の位置。**タスクが0件の列にも落とせる** |
| 落ちる位置の予告 | **ドラッグ中、挿入される位置に線を出す。** どこに落ちるか分からないまま指を離させない。見せ方は [画面設計](design/ui.md) 3章 |
| 落ちる位置の決め方 | **ポインタのY座標。** カードの中線より上ならそのカードの手前、どの中線にも届かなければ末尾 |
| 「完了」列 | **移動元・移動先の両方向で扱えること。** 完了への移動と、完了からの差し戻し（UC-03）の両方が成立する必要がある |
| 中断 | ドロップ可能な範囲の外で離した場合、移動しない |
| **キーボード操作** | **掴む → 動かす → 置く**をキーボードだけでも行える。落ちる位置の線も同じように出る |

### 3.3 詳細モーダルからのリスト移動（F-23）

| 項目 | 仕様 |
| --- | --- |
| 表示位置 | 詳細モーダル内、**タイトル欄の上**。そのタスクが現在どの列にあるかを最初に示す |
| 選択肢 | **「完了」を含むすべてのリスト。** 除外するものはない |
| 移動先での位置 | **末尾。** 列内の位置を指定する手段がないため |
| 反映のタイミング | `[ 保存 ]` を押したとき。タイトル・説明文・期限の変更と同時に確定する |
| 変更しなかった場合 | 元のリストのまま。`position` も変えない |

> **移動先を末尾にする理由。** 先頭に入れると、追加（F-06）と同じ位置に積み上がって既存の並びを乱す。**「移動」は利用者が意図的に行き先を決める操作なので、既存のタスクを押しのけない末尾が穏当**と判断した。位置まで調整したい場合はドラッグ&ドロップを使う。

### 3.4 ホバーでの完了操作（F-22）

| 項目 | 仕様 |
| --- | --- |
| 出る場所 | **「完了」以外の列のタスク。** 完了列のチェックは選択（1.4）のままで、意味が入れ替わる |
| 出し方 | **1.4 の選択チェックと同じ。** 普段はカードの下に隠れており、ホバーまたはフォーカスで現れる。露出時はカードが右へ 12px 寄る |
| 押した結果 | そのタスクが**「完了」列の先頭**へ移る |
| チェックの状態 | **入ったままにならない。** 押した瞬間に行が完了列へ移るため |
| 応答待ちの間 | 他の操作と同じく止める |

**移動先を先頭にする理由。** F-06（追加したタスクは列の先頭に入る）と揃える。完了列が長くても、スクロールせずに「いま完了にしたもの」が見える。**末尾に足す F-23（3.3）とはここが違う** — F-23 は行き先を利用者がその都度選ぶ「移動」だが、F-22 は行き先が固定の「完了させる」であり、直前の結果が見えることの方が効く。

**出し方を選択チェックと揃える理由。** 列によって作法が変わると、同じ盤面の中で操作の予測が立たなくなる。**その結果、チェックボックスはどの列のタスクにも出ることになり、違うのは意味だけになった。**

**F-15 を置き換えない。** 完了列を整理する手段は別途必要（UC-04）。**F-23 の代わりにもならない** — 「完了列へ入れる」方向だけを扱うため、差し戻しには使えない。

### 3.5 共通の仕様

**自動ソート機能は実装しない**（対象外）。並び順はすべて手動で決める。

並び順の内部表現と再採番の方式は [データベース設計](design/database.md) の「position の採番方式」を参照。**F-13・F-23・F-22 は同じ再採番ロジック・同じAPI（`PATCH /api/cards/move`）を使う。** 入力手段が違うだけで、行われる操作は同一のため。

## 4. 誤操作・エラーへの対策

### 4.1 誤操作

削除操作（タスク削除・リスト削除・完了列の選択削除）の前に確認ダイアログを出す。
Undo（元に戻す）機能は実装しない。

**確認ダイアログはブラウザ標準の `confirm()` ではなく、画面内のモーダルとして実装する。**

| 項目 | 仕様 |
| --- | --- |
| 文言 | **削除対象を名前または件数で示し、取り消せないことを明記する。** リスト削除では**道連れになるタスクの件数**も出す |
| 初期フォーカス | **「キャンセル」に置く。** 開いた直後に Enter を押しても削除されないようにする |
| 実行ボタン | 赤系。ラベルは「削除する」 |
| 閉じ方 | キャンセル、`Esc`、背景クリック |

> **標準ダイアログを使わない理由が2つある。** ①文言の作り込みができず、対象や取り消せないことを十分に伝えられない ②**環境によっては抑止され、何も起きない**。実際、画面モックを Cursor 内蔵ブラウザ（Webview）で開いた際、`confirm()` も `prompt()` も表示されず操作できなかった。

### 4.1.1 名前の入力

タスクの追加（F-06）、リストの追加（F-02）、リスト名の変更（F-03）で名前を入力する場面も、**画面内のモーダルとする**。`prompt()` は使わない。

**`prompt()` では文字数カウンタ（E-01）を出せないため、そもそも仕様を満たせない。**

| 項目 | 仕様 |
| --- | --- |
| 文字数カウンタ | 入力欄の右下。上限で入力停止・赤字（2.9 と同じ扱い） |
| 確定 | 実行ボタン、または `Enter` |
| 空文字 | **受け付けない。** 入力欄の直下にその旨を表示する（別のダイアログは出さない） |
| 閉じ方 | キャンセル、`Esc`、背景クリック、`✕` |

### 4.2 通信エラー

DB とバックエンドを挟んだことで、**保存が失敗しうる状態**が新たに発生した。特に P-4（利用者自身がサーバーを起動する）を前提とするため、**起動を忘れたままブラウザを開く**ケースは日常的に起こる（UC-01）。

#### 失敗の種類による出し分け

| 状況 | 判別方法 | 表示するメッセージ |
| --- | --- | --- |
| バックエンドに接続できない | リクエスト自体が失敗する | **「サーバーが起動していません。起動してから再読み込みしてください」** |
| バックエンドは動作しているが DB に接続できない | サーバーが 5xx を返す | **「データベースに接続できません。Docker が起動しているか確認してください」** |
| 入力内容が検証で拒否された | サーバーが 4xx とメッセージを返す | 何が不正かを具体的に表示する |
| 想定外のエラー | 上記以外 | 「エラーが発生しました」＋ サーバー側のログに詳細を出力 |

#### 発生タイミングによる出し分け

| タイミング | 挙動 |
| --- | --- |
| **初期読み込みの失敗** | 画面に表示できる内容がないため、**全面にエラーメッセージと「再読み込み」ボタン**を表示する |
| **操作中（追加・編集・削除・移動）の失敗** | 画面は表示されているため、**画面上部にメッセージを表示**し、**楽観的更新をロールバックする** |

> **ロールバックは必須。** 画面へ先に反映してから保存する実装（楽観的更新）で失敗時に戻さないと、「画面上は移動したのに、リロードすると元に戻る」という食い違いが残る。利用者はどちらが本当のデータか判断できなくなる。

画面上の見え方は [画面設計](design/ui.md) の「エラー時の表示」を参照。

#### 対象外

自動リトライ機能は実装しない。利用者が原因（サーバー未起動など）を解消したうえで、手動で操作をやり直す。

| F-01 | 初期表示 | アプリを開くと TODO / 進行中 / 完了 の3列が表示される |
| F-02 | 列の追加 | 「+ リスト追加」で**入力モーダル**が開き、名前を入れると**「完了」の左隣**に列が増える。文字数カウンタが出る。**入口は編集モードの中**（1.6） |
| F-03 | 列の名前変更 | 追加した列は改名できる。**リスト名の左端にある編集アイコンから「リストの詳細モーダル」が、現在の名前が入った状態で開く。** デフォルト3列には編集アイコンが出ない。**編集アイコンが出るのは編集モードの中だけ**（1.6） |
| F-04 | 列の削除 | 追加した列は確認後に削除できる。中のタスクも削除される。**削除は「リストの詳細モーダル」の中にあり**、確認モーダルには**道連れになるタスクの件数**が出る。デフォルト3列には編集アイコンが出ないので、そもそも開けない。**入口は編集モードの中**（1.6） |
| F-05 | 列の並び替え | 「完了」以外の列を左右に動かせる。「完了」より右へは移動できず、完了自身も動かせない。**`[←] [→]` が出るのは編集モードの中だけ**（1.6） |
| F-06 | タスクの追加 | **「完了」列を除く各列の最上部にある**「+ タスク追加」で**入力モーダル**が開き、タイトルを入れると**そのすぐ下（列の先頭）に追加される**。スクロールせずに追加結果を確認できる |
| F-07 | タスクの詳細ポップアップ | タスクをクリックするとポップアップが開き、タイトル・説明文・期限を編集して保存できる。**改行を含む説明文が、改行を保った状態で再表示される** |
| F-08 | タスクの削除 | **期限と同じ行の右端にあるゴミ箱アイコン**から、確認モーダルの後に削除される。**アイコンはタスクの文字色に追従し、赤いタスクでも完了列でも判別できる** |
| F-09 | 期限の入力 | 年月日は必須、時分は任意で入力できる |
| F-10 | 期限の表示 | 月日時分はゼロ埋めで表示する。時分なしは時分を出さない。今年と異なる年のときだけ年を表示する |
| F-11 | 期限の色分け | 期限超過・当日は赤ボーダー＋赤背景＋白文字、翌日は赤ボーダー、2〜3日以内は黄ボーダーになる。完了列のタスクは期限に関わらず薄いグレー＋黒文字になる |
| ~~F-12~~ | ~~ボタンでのタスク移動~~ | **欠番。実装しない。** 理由は [要件定義書](requirements.md) の「機能一覧」を参照 |
| F-13 | タスクのドラッグ&ドロップ | 別の列・列内の任意の位置へドラッグして移動できる。**ドラッグ中、落ちる位置に線が出ること。線の位置と実際に落ちる位置が一致すること。** タスクが0件の列にも落とせること。**カードとカードの隙間にポインタがあっても、その隙間が落ち先になること**（末尾に飛ばない）。**「完了」列を移動元・移動先の両方向で扱えること**（＝ UC-03 の差し戻しがドラッグだけで成立すること）。移動後、期限による色分けが移動先に応じて更新されること。**掴む・動かす・置くをキーボードだけでも行え、そのときも線が出ること** |
| ~~F-14~~ | ~~完了列の件数制限~~ | **欠番。実装しない。** F-25 に置き換えた。理由は [要件定義書](requirements.md) の「機能一覧」を参照 |
| F-15 | 完了タスクの選択削除 | チェックしたタスクを確認後にまとめて削除できる。全選択も可能 |
| F-16 | データの永続化 | すべての変更が PostgreSQL に保存され、ブラウザ・サーバー再起動後も保持される |
| **F-23** | **詳細モーダルからのリスト移動** | モーダル内のリスト選択欄で移動先を選び、`[ 保存 ]` を押すと**そのリストの末尾へ移動する**。「完了」も選択でき、「完了」から他のリストへの差し戻しもできる。**マウスを使わず、キーボードだけで一連の操作を完了できること** |
| **F-22** | **ホバーでの完了操作** | 「完了」以外の列のタスクにホバーまたはフォーカスすると**チェックボックスが現れ**、チェックすると**そのタスクが「完了」列の先頭へ移動する**。完了列のチェックは選択（F-15）のままで、完了へは移らない。**マウスを使わず、キーボードだけでも操作できること**。応答待ちの間は反応しないこと |
| **F-25** | **列内スクロール** | 盤面がウィンドウの高さに収まり、**ページ全体が縦にスクロールしない**。タスクが入りきらない列は**その列の中だけがスクロールする**。どれだけスクロールしても、**ボード名・リスト名・`[+ タスク追加]`（編集モード中は `[←] [→]` と編集アイコンも）は隠れない**。列が0件でも、タスクが1件でも、列の見出しの位置は揃っている |
| **F-24** | **リストの編集モード** | ボード見出しの横の `[ リストを編集する ]` でモードに入り、**同じボタンか `Esc` で抜ける**。**モード外では `[←] [→]`・編集アイコン・`[+ リスト追加]` がどれも出ない**（盤面に出るのはリスト名とタスクだけ）。**モード中はタスクの操作がすべて止まる** — カードを掴めず、チェックも押せず、`[+ タスク追加]` もゴミ箱も反応しない。**モードの出入りでスクロール位置とタスクの並びが変わらないこと** |
| **F-21** | **列のドラッグ&ドロップ** | 編集モード中、**列全体を掴んで**左右に動かせる。**落ちる位置に縦の線が出て、線の位置と実際に落ちる位置が一致すること。** 「完了」列は掴めず、**他の列を「完了」より右へは落とせないこと。** **掴む・動かす・置くをキーボードだけでも行え、そのときも線が出ること。** 並び替えの結果が再読み込み後も保持されること |

### 5.2 入力・エラー処理

| ID | 機能 | 受け入れ条件 |
| --- | --- | --- |
| E-01 | 文字数カウンタ | タイトル・説明文・リスト名の入力欄に `12/100` 形式で文字数が表示される。上限に達すると入力が止まり、文字数の表示が赤色になる |
| E-02 | 上限超過の貼り付け | 上限を超える文字列を貼り付けると、上限までで切り詰められる |
| E-03 | サーバー未起動時 | サーバーを起動せずにアプリを開くと、全面にエラーと「再読み込み」ボタンが表示される |
| E-04 | DB未起動時 | サーバーのみ起動し DB のコンテナを停止した状態で操作すると、Docker の起動を促すメッセージが表示される |
| E-05 | 操作中の通信失敗 | 移動・編集の途中で通信が失敗すると、画面上部にメッセージが出て、**画面の表示が操作前の状態に戻る** |
