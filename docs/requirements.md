## 2. 用語

```
ボード (Board)    … 一番外側の入れ物。1個のみ
 └ リスト (List)   … 縦の列
    └ タスク (Task) … やること1件
```

### 2.1 「タスク」と `cards` の対応

**利用者に見える名称・本文書群の記述は「タスク」に統一する。** 一方、**DBのテーブル名とAPIのパスは `cards` のままとする。**

| 層 | 呼び方 |
| --- | --- |
| 画面の文言、本文書群の本文 | **タスク** |
| DBのテーブル・列 | `cards`, `cards.list_id` など |
| APIのパス | `/api/cards`, `/api/cards/move` など |

> **名称を層で分けている理由。** 利用者にとっては「タスク管理アプリ」で扱うものが「カード」と呼ばれるのは回りくどい。一方 Trello 系のボードUIにおいて `cards` は事実上の一般名詞であり、実装時に参照する記事やライブラリはこの語を使う。内部識別子まで `tasks` に寄せると、外部の資料との照合が一段増える。**この対応表があれば読み替えは1箇所で済む。**

**画面はボード画面1つのみ。** 認証を対象外としたため、ログイン画面は存在しない。画面の詳細は [画面設計](design/ui.md) を参照。

## 3. 前提条件とスコープ境界

### 3.1 前提条件

以下を前提とする。前提が崩れた場合は要件の再検討が必要となる。

| # | 前提 | 崩れた場合の影響 |
| --- | --- | --- |
| P-1 | 利用者は1名のみ | 共有・権限管理の要件が発生する |
| P-2 | **外部公開せず、利用者のPC内でのみ動作する** | **認証が必須になる。** あわせてセキュリティ要件・可用性要件が全面的に発生する（「将来の拡張」の章を参照） |
| P-3 | 利用端末はPCのブラウザのみ | スマートフォン対応が必要になる |
| P-4 | **利用開始時に、サーバーの起動操作を利用者が行える** | 起動を自動化する仕組みが必要になる |
| P-5 | データは利用者のPC内にのみ存在する | — |

> **P-4 は DB 採用に伴って新たに発生した制約。** LocalStorage 方式では「ブラウザで開くだけ」だったものが、利用のたびに起動操作を要するようになった。利用者にとっての手間が増えている点を前提条件として明示する。手順は [運用手順](operations.md) に記載する。
>
> **起動が必要なのは3つ**（PostgreSQL のコンテナ、バックエンドの Spring Boot、フロントエンドの Vite 開発サーバー）。DB は `docker compose up -d` の1コマンドで済む（7.4 を参照）。

### 3.2 対象に含むもの

- 単一ボードでのタスク管理（リスト・タスクの作成／編集／削除、並び替え、期限管理）
- PostgreSQL によるデータの永続化
- バックエンド API の実装

### 3.3 対象に含まないもの

| 除外するもの | 理由 | 利用者への影響 |
| --- | --- | --- |
| **ログイン認証** | 利用者1名（P-1）かつ外部公開しない（P-2）ため、保護すべき対象がない。**ローカル環境では認証を設けてもDBへ直接接続すれば全データが参照できるため、アクセス制御としても機能しない** | アプリを開くと即座にボードが表示される |
| 共有・共同編集・権限管理 | 利用者1名（P-1） | 他者とタスクを共有できない |
| スマートフォン対応 | PCブラウザのみ（P-3） | **外出先でタスクを確認・更新できない** |
| 端末間のデータ同期 | **技術的には可能だが、意図的にスコープ外とする。** 実現するには P-2 の境界を越える必要がある | 別のPCからは利用できない |
| データのバックアップ機能 | MVP の範囲外（F-20） | **PC故障・DB破損時にデータを全て失う。** 必要な場合は [運用手順](operations.md) の手順で利用者自身が退避する |
| Undo（元に戻す） | 削除前の確認ダイアログで代替する | 誤って確定した削除は復元できない |
| 優先度の設定 | タスクのタイトルの付け方で代替できる | — |
| ソート機能（期限順・作成日順） | 手動の並び順と競合するため | 期限が近い順に自動で並べ替えることはできない |
| ファイル添付・メール通知 | 目的に対して不要 | — |

## 4. 利用シナリオ

正式なユースケース記述（事前条件・代替フロー・例外フローを網羅する形式）ではなく、**機能をまたいだ操作の流れ**を示す。

**機能一覧が「部品が揃っているか」を示すのに対し、本章は「その部品で目的を達成できるか」を確認するためのもの。** 機能単位で仕様を書いていると、機能と機能のつなぎ目が抜けやすい。

アクターは利用者本人1名のみ（P-1）。

### 4.1 UC-01 利用を開始する

**事前条件**: PC が起動している

| # | 操作 | 結果 |
| --- | --- | --- |
| 1 | Docker Desktop を起動し、PostgreSQL のコンテナを立ち上げる | DB が接続可能になる |
| 2 | バックエンドサーバー（Spring Boot）を起動する | API が応答可能になる |
| 3 | フロントエンドの開発サーバー（Vite）を起動する | `localhost:3000` が応答可能になる |
| 4 | ブラウザで `localhost:3000` を開く | ボードの取得処理が実行される |
| 5 | — | ボード画面が表示される（F-01） |

**事後条件**: ボードが操作可能な状態になる

**代替フロー**

| 分岐 | 挙動 |
| --- | --- |
| 2 を実行していない | 全面エラー「サーバーが起動していません」＋再読み込みボタン（E-03） |
| 1 を実行していない | 全面エラー「データベースに接続できません」（E-04） |

> **この手順は P-4 そのもの。** 利用のたびに毎回必要になるため、[運用手順](operations.md) に起動手順を記載する。手順が文書化されていないと、しばらく使わなかった後に起動方法が分からなくなる。

### 4.2 UC-02 タスクを登録し、完了させる

最も基本的な流れ。

| # | 操作 | 結果 | 関連 |
| --- | --- | --- | --- |
| 1 | TODO 列の `[+ タスク追加]` にタイトルを入力 | **列の先頭**にタスクが追加される | F-06 |
| 2 | タスクをクリック | 詳細モーダルが開く | F-07 |
| 3 | 説明文と期限を入力し、`[ 保存 ]` | 内容が保存され、一覧にタイトルと期限が表示される | F-07, F-09 |
| 4 | — | 期限までの残り日数に応じてタスクの色が変わる | F-11 |
| 5 | 着手時、タスクを「進行中」列へドラッグする | 「進行中」列へ移動する | F-13 |
| 6 | 完了時、さらに「完了」列へドラッグする | 「完了」列へ移動し、**色分けが薄いグレーに統一される** | F-13 |

**事後条件**: タスクが「完了」列に入り、期限による警告色が消える

> **手順5・6は詳細モーダルからでも行える**（F-23）。マウスを使わずに操作したい場合、およびドラッグしにくい状況ではこちらを使う。

### 4.3 UC-03 完了したタスクを差し戻す

誤って完了にした場合、または作業をやり直す場合。

| # | 操作 | 結果 |
| --- | --- | --- |
| 1 | 「完了」列の対象タスクを、左隣の列へドラッグする | 「完了」の左隣の列へ移動する |
| 2 | — | 期限による色分けが復活する |

**「完了」列のタスクも、他の列と同じ手段で移動できなければならない。** 手段は2つあり、どちらでも差し戻せる。

| 手段 | 内容 |
| --- | --- |
| ドラッグ&ドロップ（F-13） | 「完了」列から他の列へドラッグする |
| 詳細モーダル（F-23） | タスクを開き、リストの選択欄で移動先を選んで保存する |

> **F-13 の実装では「完了」列を移動元・移動先の両方向で扱えることが必須条件となる。** 片方向しか動かないと、このシナリオがドラッグでは成立しなくなる。
>
> なお F-22（ホバーでの完了操作）は「完了列へ入れる」方向だけを扱うため、差し戻しの手段にはならない。
>
> **チェックボックスはどの列のタスクにも出る**（ホバーまたはフォーカスで露出）。**違うのは意味で、完了列では一括削除のための選択（F-15）、それ以外の列では「完了にする」（F-22）。**

### 4.4 UC-04 完了列を整理する

完了したタスクは削除しない限り蓄積し続けるため、定期的な整理を前提とする。

| # | 操作 | 結果 |
| --- | --- | --- |
| 1 | 完了列がウィンドウの高さを超える | 収まる分だけ表示され、**続きは列の中のスクロールで見える**（F-25） |
| 2 | 削除したいタスクのチェックボックスを入れる | 選択状態になる（**DBには保存されない**） |
| 3 | `[〇件を削除]` を押す | 確認ダイアログが表示される |
| 4 | 確認する | 選択したタスクがまとめて削除される（F-15） |

> **完了タスクの自動削除・保持期間の仕組みは存在しない。** 削除は利用者の手動操作のみ。したがって F-15 は「あると便利な機能」ではなく、**溜まった完了タスクをまとめて片付ける手段**である。
>
> **1件ずつの削除は F-08（カード上のゴミ箱アイコン）が担う。** ゴミ箱は完了列のタスクにも出るので、F-15 が無くても完了列を減らすことはできる。F-15 が引き受けているのは**まとめて片付けること**であり、そこを取り違えると F-15 の重みづけを誤る。

**全件を削除したい場合**は `[全選択]` を使う。専用の「全件削除」ボタンは設けない。

> **手順2（チェックを入れる）を飛ばせない。** チェックボックスと `[全選択]` はどちらも、**1件も選ばれていない状態では画面に出ない**（[画面設計](design/ui.md) 1章）。全件削除であっても、まず1件は手で選ぶことになる。**意図的にそうしている** — 全件の削除が確認ダイアログ1枚で到達できるより、一手挟む方が誤操作を抑えられる。

### 4.5 UC-05 作業の流れに合わせて列を増やす

| # | 操作 | 結果 |
| --- | --- | --- |
| 1 | `[+ リスト追加]` に名前を入力 | **「完了」の左隣**に列が追加される（F-02） |
| 2 | 列見出しの `[←] [→]` を押す | 列の位置を調整する。「完了」より右へは移動できない（F-05） |
| 3 | 不要になったら `[削除]` を押す | 確認ダイアログの後、**中のタスクごと削除される**（F-04） |

> 手順3で中のタスクが消えることは、確認ダイアログの文言で明示する。タスクを残したい場合は、事前に他の列へ移動しておく必要がある。

> **F-24 の実装後は、手順1の前に「ボード見出しの横の `[ リストを編集する ]` を押す」が入る。**（2026-08-31 決定、#89）上の3手順は**どれもモードの中**の操作になる。**シナリオそのものは変わらない** — 変わるのは入口だけで、できることは同じ。5.2 の F-24 を参照。

### 4.6 シナリオから確認できたこと

| 確認項目 | 結果 |
| --- | --- |
| 起動から利用開始までの流れ | **[運用手順](operations.md) への記載が必要** |
| 完了からの差し戻し | 完了列のタスクも他の列と同じ手段で移動できる必要があると判明。[画面設計](design/ui.md) と [機能仕様書](functional-spec.md) に反映済み。**F-13 の受け入れ条件に「完了」列の双方向対応を含めた** |
| タスクを残して列を削除する手段 | **専用機能はない。** 事前に手動で移動する運用でよいと判断 |
| 期限切れタスクの一覧表示 | **できない。** ソート・絞り込みは対象外（F-18） |

>

> **F-14 は欠番。一度も実装しない。**（2026-08-29 決定、#64）
>
> F-14 は「完了列を9件まで表示し、10件目が上部だけ覗く。『もっと見る』で全件展開できる」という機能だった。これを取り下げ、**F-25（列内スクロール）に置き換える。**
>
> **気づいた経緯。** F-14 の実装中、覗く高さを決めるために完了列へ12件入れて実際に触った。ウィンドウを広げた状態では良く見えたが、**ウィンドウを縮めたとき、ボード名が隠れるほどのスクロールが必要になることに気づいた。** ヘッダーを固定してもリスト名が流れていき、**列が多いとどこに入れようとしていたか分からなくなる。** 根本は「盤面の高さが画面に収まっていないこと」であり、これは完了列に限らずどの列でも起きる。
>
> **F-14 として書けるものが残らなくなった。** 変化が2つ重なったため。①**適用範囲**が完了列だけから全列に広がり、「完了列の特別扱い」ではなくなった ②**件数**が固定の9件からウィンドウの高さ依存になり、名前が指している「件数制限」そのものが消えた。目的（完了列が無限に伸びるのを止める）はウィンドウの高さが担保するため、目的は F-25 で満たされる。
>
> **採らなかった案が3つある。** ①**リスト名だけを `position: sticky` で貼る** — 見出しをスクロール領域の外の兄弟に置けば貼る必要がない ②**最大高さを「9件分」にする** — 「1行カードの9件ぶん」という**根拠の書けない定数**が残り、タイトルは折り返すため実際に見える件数もぶれて「9件」が保証にならない ③**ドラッグ中の自動スクロールを用意する** — 移動先を事前にスクロールしておけるため不要。
>
> **番号は詰めずに欠番とする。** 理由は F-12 と同じ。
>
> **F-15 は影響を受けない。** 完了列の特別扱いがすべて消えるわけではなく、選択削除・全選択・タスクの移動は残る。UC-04 も、溜まった完了タスクをまとめて片付ける手段が F-15 である以上そのまま成立する。

> **F-25 の内容。**（2026-08-29 記録、#64）**盤面をウィンドウの高さに収め、はみ出す列はその列の中でスクロールさせる。**
>
> | 項目 | 内容 |
> | --- | --- |
> | 適用範囲 | **全列。** 完了列に限らない |
> | 表示件数の上限 | **設けない。** 見える件数はウィンドウの高さ次第 |
> | スクロールする範囲 | **タスク一覧の領域だけ。** 並び替えの矢印・リスト名・`[+ タスク追加]` はスクロール領域の外に置くため、**どれだけスクロールしても隠れない** |
>
> **これが要件である理由。** 列が多いボードでは、どの列に入れようとしているかが常に分かる必要がある。リスト名が流れて見えなくなると、その判断ができない（6.6 のユーザビリティ要件）。

> **F-24 の内容。**（2026-08-29 記録）ボードの見出しの横に `[ リストの配置を編集する ]` を置く。押すとモードに入り、**その間だけ**各列に `[←] [→]` が現れる。キーボードでは列を選んで `←` `→` で動かし、`Esc` で終了する。マウスとキーボードで**入口も操作も同じ**になる。
>
> **利点は3つ。** ①**列見出しにボタンを常設せずに済む** — 260px しかない列幅をリスト名と奪い合わないので、名前が `…` で切れにくくなる ②**操作の入口が1つに揃う** ③**デフォルト3列も対象にできる**（リストの詳細モーダルに入れる案も検討したが、**デフォルト3列にはモーダルの入口が無く**、TODO・進行中をキーボードで動かす手段が消えるため採らなかった）。
>
> **MVP に入れない理由。** モードの状態管理・選択中の列の表示・`Esc` での離脱・支援技術への通知が要り、**常設ボタンに比べて実装が一段大きい。** 得られるのは操作性の改善であり、**「並び替えられる」こと自体は F-05 の常設ボタンで満たせている。**
>
> ~~**検討するのは F-21 の後。** F-21（列のドラッグ&ドロップ）で dnd-kit を入れると、そのキーボードセンサーが「掴む → 矢印で動かす → 置く」を標準で提供する（7.2 で dnd-kit を選んだ理由がこれ）。**先に F-24 を自作すると、F-21 で重複する可能性がある。**~~

> **F-24 と F-21 は1つの機能として作る。**（2026-08-30 決定、#84）
> **F-24 のモードを入口にし、その中で F-21（列のドラッグ&ドロップ）を使う。** モード中は `[←] [→]` も出し、**ドラッグとキーボードの両方で動かせる**ようにする。**モード外では `[←] [→]` を出さない。**
>
> **`[←] [→]` を残す理由。** ドラッグ&ドロップはマウスを専有する操作であり、これだけにすると**キーボードで列を動かせなくなる。** タスクの移動で F-23 を残したのと同じ考え方（5.3・6.6）。
>
> **モード外で消す理由。** いまは列見出しの上に常設しており、**300px しかない列幅とリスト名の読みやすさを常時消費している。** 並び替えは滅多に行わない操作なので、必要なときだけ出す方が釣り合う。
>
> **上の「検討するのは F-21 の後」は失効した。** **dnd-kit は F-13（Step 11）で既に入っており**、「F-21 で dnd-kit を入れると」という前提そのものが過去のものになったため。**キーボードセンサーは今すぐ使える。** 打ち消し線で残したのは、判断がいつ何によって変わったかを追えるようにするため。

> **F-24 の範囲を、リストに関する操作すべてへ広げる。**（2026-08-31 決定、#89）
> **v1.10 では並び替え（F-05・F-21）だけをモードに入れる予定だった。** そこへ **F-02（追加）・F-03（改名）・F-04（削除）を加える。**
>
> | | モード外 | モード中 |
> | --- | --- | --- |
> | 列の見出し | **リスト名だけ** | リスト名 ＋ `[←] [→]` ＋ 鉛筆（F-03 / F-04） |
> | 列の並び替え | できない | ドラッグ&ドロップ（F-21）＋ `[←] [→]`（F-05） |
> | リストの追加（F-02） | **出さない** | `[+ リスト追加]` を盤面の右端に出す |
> | タスクの操作 | すべてできる | **すべて止める** |
>
> **ねらいは、平時のタスク管理を視覚的にも操作感的にも邪魔しないこと。** リストへの操作はどれも頻度が低いのに、いまは**列ごとに矢印の行と鉛筆、盤面の右端に `[+ リスト追加]`** が常に場所を取っている。**モード外の盤面に残るのがリスト名とタスクだけ**になれば、「リストへの操作はすべてモードの中、モード外はタスク管理だけ」と一言で説明でき、覚えることが1つで済む。
>
> **`[+ リスト追加]` も入れる理由。** これだけモード外に残すと、**原則に例外が1つできる。** 盤面の右端で常時 300px（列と同じ幅）を取っている点も、他の入口と事情が同じ。
>
> **行き止まりにはならない。** デフォルトの3列は必ず存在するので、「モードに入らないとボードが空のまま」という状態は起きない。
>
> **モード中はタスク側の操作をすべて止める。** 列を掴む操作は現実的に**列全体を掴む**形になるが、その内側にはカードのドラッグ（F-13）・ホバーのチェック（F-22）・選択（F-15）・`[+ タスク追加]` が載っており、**押したいのがどちらなのかが決まらない。** 止めることで「いまはリストを並べる時間」であることも見た目で伝わる。
>
> **5.1 の F-02〜F-05 は MVP のまま動かさない。** 機能そのものは無くならず、**入口だけが変わる**ため。5.1 から外すと「MVP に無かった」ことになって経緯が読めなくなる（F-22 を 5.2 に残したのと同じ扱い）。
>
> **4.5（UC-05）の手順は、入口が変わるぶん書き換わる。** 手順1の前に「`[ リストを編集する ]` を押す」が入る。
>
> **モードを抜けるときに「保存しますか」は聞かない。**（2026-08-31 決定、#91）
> **一度は必要だと考えた。** 「間違えたまま抜けてしまうのではないか」という懸念からだが、**このモードで触れるのはリストだけで、タスクには影響しない**ため、当てはまらないと判断した。
>
> | 操作 | 間違えたときにどうなるか |
> | --- | --- |
> | 並び替え（F-05 / F-21） | **位置がずれるだけ。** その場で戻せる |
> | 改名（F-03） | 入力画面を挟むので、確定する前に気づく |
> | 削除（F-04） | **確認モーダルが、道連れになるタスクの件数を出して止める**（4.3） |
>
> **致命的なものが1つも無いので、出口で改めて聞く必要がない。**
>
> **そもそも聞ける形になっていない。** この画面は**操作した瞬間に保存する**作りで、モードを抜ける時点ではすべて保存済み。聞けるようにするには**保存を後回しにする（下書きにする）**設計変更が要り、それはこの判断とは別の話になる。

### 5.3 移動手段の考え方

**タスクの移動手段は F-13（ドラッグ&ドロップ）と F-23（詳細モーダル）の2つ。どちらも恒久機能であり、片方が片方を置き換えることはない。**

| 機能 | 位置づけ |
| --- | --- |
| F-13 ドラッグ&ドロップ | **主たる手段。** 列内の任意の位置を指定でき、操作が直感的 |
| F-23 詳細モーダルからのリスト移動 | **補完する手段。** 列は選べるが、列内での位置は選べない（末尾に入る） |

**F-23 を MVP に入れる理由は3つある。**

| 理由 | 内容 |
| --- | --- |
| **アクセシビリティ** | **ドラッグ&ドロップはマウスを専有する操作であり、キーボードだけでは実行できない。** F-13 が唯一の移動手段だと、「ユーザビリティ・アクセシビリティ」の要件に対して退行する。F-23 は選択欄なので、キーボードだけで移動できる |
| **実装順序** | F-23 は入力手段が単純なため、**`position` の再採番と移動APIを、ドラッグ&ドロップの難しさと切り離して先に完成させられる**。F-12 が担うはずだった足場の役割を、捨てずに済む形で果たす |
| **実用ラインの維持** | [開発計画](development-plan.md) は「Step 8 で実データを入れて使い始められる」ことを狙っている。移動できないボードは使えないため、この時点で何らかの移動手段が要る |

### 5.4 MVP後の機能どうしの関係

| 関係 | 内容 |
| --- | --- |
| F-13 → F-22 | F-22 は F-13 の後に置く。ドラッグ&ドロップでの操作感を見てから、近道の必要性を判断する |
| F-22 ⇏ F-15 | F-22 は F-15 を置き換えない。両方を残す |
| F-22 ⇏ F-23 | F-22（ホバーでの完了操作）は「完了列へ入れる」方向だけを扱うため、差し戻しには使えない。F-23 の代わりにはならない |

### 5.5 対象外

ログイン認証、共有・共同編集・権限管理、スマートフォン対応、端末間同期、ファイル添付、通知、Undo、優先度、自動ソート。

### 6.4 セキュリティ

P-2（外部公開しない）かつ認証を持たないため、実装するのは以下に限定する。

| 項目 | 要件 |
| --- | --- |
| 入力値の検証 | **サーバー側で必ず行う。** ブラウザ側の検証は補助であり、迂回可能なため信頼しない |
| SQLインジェクション対策 | **ORM を使用し、文字列連結で SQL を組み立てない。** プレースホルダによる直接記述でも安全性は同等だが、ORM は危険な書き方が構造的にしにくいため採用する |
| 発行SQLの可視化 | **ORM が発行する SQL をログ出力する設定を有効にする。** 裏で何が実行されているか把握できないままだと、DB を学ぶという目的が損なわれるため |
| XSS対策 | **説明文・タイトルは HTML として解釈せず、必ずエスケープして表示する** |
| 機密情報の管理 | DB接続情報は環境変数で管理し、**リポジトリにコミットしない** |

**対象外**: 認証・セッション管理、HTTPS通信、CSRF対策、脆弱性の定期監査。いずれも P-2 を前提とした判断であり、**公開する場合は認証を含めて必須となる**（「将来の拡張」の章を参照）。

### 6.6 ユーザビリティ・アクセシビリティ

| 項目 | 要件 |
| --- | --- |
| 文字色と背景色のコントラスト比 | **4.5:1 以上**（WCAG 2.1 レベルAA相当） |
| **色だけで伝える情報を作らない** | **色分けは、文字でも読み取れる情報を補強する用途に限る。** この原則を守っている限り、装飾としての色は 3:1 を満たさなくてよい（下の但し書きを参照） |
| **ポインタ操作以外の移動手段** | **タスクの移動を、ドラッグ&ドロップ以外の手段でも行えるようにする。** ドラッグ&ドロップはマウスを専有する操作であり、これしか無いとキーボードだけでタスクを移動できなくなる。詳細モーダルのリスト選択欄（F-23）がこの要件を満たす。**あわせて、ドラッグ&ドロップ自体もキーボードで行える**（下の但し書きを参照） |
| 操作可否の明示 | 移動できない方向の操作は、無効状態を視覚的に示す（列の並び替えボタンなど） |
| 削除の取り消し | 実装しないため、確認ダイアログの文言で対象を明示する |
| 説明文の改行 | 入力どおりに表示へ反映する |

> **タスクの移動は、ドラッグ&ドロップ自体もキーボードだけで行える。**（2026-08-30、#74）
> カードにフォーカスして `Space` で掴み、矢印で動かし、もう一度 `Space` で置く。落ちる位置の線も同じように出る。**dnd-kit のキーボードセンサーが土台を提供する**ため、F-13 と同時に手に入った（7.2 でこのライブラリを選んだ理由がこれ）。
>
> **ただし、標準のままでは成立しなかった。**（2026-09-01 追記、#93 / #97）**「次にどこへ動かすか」を決める計算は、列の並び替えでもタスクの移動でも自前に置き換えている。** 標準の計算は**登録されている受け口をすべて候補にし、押した向きと距離だけで選ぶ**ので、**列を区別せず、受け口の形も問わない。** 実際、列の並び替えで3件・タスクの移動で5件の不具合として現れた（[開発計画](development-plan.md) の Step 12 の補足）。
>
> **ライブラリを選んだ判断そのものは変えない。** 入力の受け取り・状態の管理・追従する本体の描画・支援技術への通知は標準のまま使えており、**差し替え口（`collisionDetection` と `coordinateGetter`）が最初から用意されていたこと**が、判断だけを自前にできた理由になっている。
>
> **それでも F-23 は残す。** 上の要件は「ドラッグ&ドロップ以外の手段」を求めており、キーボードで動く**ドラッグ&ドロップ**はその代わりにならない。加えて F-23 は、選択欄で行き先を選ぶという**まったく別の操作の形**を提供している。位置づけは [機能仕様書](functional-spec.md) 3.1 のとおり変わらない。

> **期限の色分け（F-11）のボーダーは、3:1 を満たさない色を使っている。**（2026-08-25 決定）
>
> 当初は「UI部品の識別に必要な 3:1 を満たすこと」を前提に色を選んでいたが、その条件下では黄・オレンジ系が暗い黄土色（`#c78500` で 3.10:1）にしかならず、**「期限が近いことに気づかせる」という色分け本来の目的を果たせなかった。** 明るくするほど白背景との差が消えるという、黄の性質による行き詰まりである。
>
> **そこで 3:1 を外し、明るい黄（`#ffca61`）を採った。** 根拠は、**期限がカード上に「08/28」と文字でも表示されている**こと。色は唯一の伝達手段ではなく、文字で読める情報を補強しているだけなので、色が見分けられなくても情報は失われない。
>
> **したがってこの但し書きは、色だけで伝える情報を作らない限りにおいて成立する。** 今後、色でしか区別できない状態を追加する場合は、この判断ごと見直すこと。
>
> なお**文字と背景の 4.5:1 は例外なく守る。** 赤背景のタスクを白文字にしているのはそのため（`#b3261e` に白で 6.5:1）。

### 7.1 指定されたもの

| 層 | 技術 |
| --- | --- |
| バックエンド | **Java** ＋ **Spring Boot** |
| フロントエンド | **React**（**Next.js は対象外**） |
| データベース | **PostgreSQL** |

### 7.2 選定したもの

| 分類 | 採用 | 選定理由 |
| --- | --- | --- |
| Java | **JDK 25（LTS）** | 最新の LTS。配布は Temurin（Eclipse Adoptium） |
| フレームワーク | **Spring Boot 4.1.x** | Spring Framework 7 ベース。Web MVC / Data JPA / Validation / Flyway を使用。**日本語の解説記事はまだ少ないため、公式リファレンスを一次情報とする前提で進める。** 4系ではスターター名が変わっている（`spring-boot-starter-web` → `spring-boot-starter-webmvc`、`spring-boot-starter-test` → モジュール別の `-test`）ため、**記事を参考にする際は依存の記述をそのまま写さないこと** |
| ビルドツール | **Gradle（Kotlin DSL）** | Gradle Wrapper（`gradlew`）を同梱するため、Gradle 本体のインストールは不要 |
| ORM | **Spring Data JPA / Hibernate** | 6.4 の「ORM を使用し、文字列連結で SQL を組み立てない」を構造的に満たす。詳細は [データベース設計](design/database.md) |
| マイグレーション | **Flyway** | 6.7 の「必ずマイグレーションファイルとして記録し、バージョン管理下に置く」を満たす。**Hibernate の `ddl-auto` は使わない**（スキーマの変更履歴が残らないため） |
| 入力値の検証 | **Bean Validation（Jakarta Validation）** ＋ `@ControllerAdvice` | 6.4 の「サーバー側で必ず行う」を満たす |
| フロントのビルド | **Vite** ＋ **React** ＋ **TypeScript** | Next.js が対象外のため SPA 構成とする |
| CSS | **Tailwind CSS**（Vite プラグイン経由） | 画面が1つでコンポーネント数も少なく、クラス名の設計規約を別途決めるより、**マークアップの隣で完結するほうが読み返しやすい。** 配色・余白の値は `mock/style.css` で実測済みのものを移す |
| Lint | **oxlint** | Vite の React テンプレートが標準で入れているものをそのまま使う。設定は `frontend/.oxlintrc.json` |
| サーバーとの通信 | **fetch API を薄くラップした自前クライアント** | エラー表示の分岐（E-01〜E-05）が独自仕様のため、ライブラリを挟むより素直。追加依存もない |
| サーバー状態の管理 | **なし**（React の状態と自前の再取得） | 画面が1つで、取得は `GET /api/board` の一括取得1本。専用ライブラリは今回の規模に対して過剰 |
| ドラッグ&ドロップ | **dnd-kit**（[開発計画](development-plan.md) の Step 11 で導入） | キーボード操作への対応が標準で付くため、6.6 のアクセシビリティ要件と方向が一致する。**「どこへ落ちるか」の判断は自前に差し替えている**（6.6 の但し書き、#93 / #97）が、**差し替え口が用意されていること自体がこのライブラリの利点**であり、選定の判断は変わらない |
| テスト（方針） | **最小限** | 「1ステップごとにブラウザで動作を確認する」開発方針を主とし、自動テストは壊れやすい箇所（`position` の再採番、入力値の検証、件数上限）に限定する。**書くのは手動確認の後・PR の前**とし、別 Issue に回さない |
| テスト（バックエンド） | **JUnit 5** ＋ Spring Boot Test ＋ **Testcontainers**（PostgreSQL） | 再採番と件数上限は**実際の DB でしか確かめられない**（一括 UPDATE と永続化コンテキストの噛み合わせを含むため）。モックの DB に置き換えると、確かめたい部分が消える。7.4 で Docker を前提に戻したので使える |
| テスト（フロントエンド） | **Vitest** ＋ **@testing-library/react**（**jsdom** 上） | Vite と同じ設定・変換をそのまま使えるため、テスト用に別のビルド構成を持たなくて済む。@testing-library を選ぶのは、**利用者から見える手がかり（見出し・ラベル・ボタン名）で書ける**ため。実装の内部構造に紐づけると、作りを変えただけでテストが落ちる |

### 7.3 構成

**フロントエンドとバックエンドを分離する。**

```
ブラウザ
  │  http://localhost:3000
  ▼
Vite 開発サーバー（React SPA）        ← npm run dev
  │  /api/* をバックエンドへ転送（プロキシ）
  ▼
Spring Boot（localhost:8080）         ← gradlew bootRun
  │  TCP  localhost:5432
  ▼
PostgreSQL（Docker コンテナ）          ← docker compose up -d
```

| 判断 | 理由 |
| --- | --- |
| **一体型（フルスタックフレームワーク）の推奨を取り下げた** | v0.10 までは一体型を推奨していたが、**指定されたスタックが Java と React の組み合わせであり、分離が前提となるため**。判断を消さず、変更として記録する |
| **利用者が開くのは `localhost:3000` のまま** | Vite 開発サーバーを 3000 番で動かし、`/api` へのリクエストだけを 8080 番へ転送する。**利用者から見た入り口が1つで済み**、あわせて CORS の設定も不要になる |
| **リポジトリは `backend/` と `frontend/` を並べる** | 単一リポジトリで管理する。既存の `docs/` と `mock/` はそのまま残す |

**利用のたびに起動するものは3つ**（PostgreSQL のコンテナ、Spring Boot、Vite）。手順は [運用手順](operations.md) を参照。

### 7.4 PostgreSQL を Docker で動かす判断

**PostgreSQL は Docker Desktop 上のコンテナで動かす。** 構成は `compose.yaml` に記述し、リポジトリで管理する。

| 項目 | 内容 |
| --- | --- |
| 実行方法 | **`docker compose up -d`** でコンテナを起動する。イメージは `postgres:17`（版を固定し、意図しない更新を防ぐ） |
| ロールとDBの作成 | `compose.yaml` の `environment` で自動作成される。**手作業の `CREATE ROLE` / `CREATE DATABASE` は不要** |
| データの保存先 | 名前付きボリューム `pgdata`。**`docker compose down -v` の `-v` を付けると消える**（[運用手順](operations.md) の注意を参照） |
| クライアントツール | `psql` / `pg_dump` は **`docker compose exec db` 経由**で使う。ホスト側への追加インストールは不要で、サーバーと版が必ず一致する |
| 利点 | 構成がバージョン管理下に入り、**PC を変えても同じ DB が立つ。** また PostgreSQL の版を上げる検証も、イメージのタグを変えるだけで済む |

> **この判断は一度撤回して戻したもの。** v1.0 では「Docker Desktop は一定規模以上の企業での利用が有償ライセンスとなるため、判断が微妙になる環境を避ける」という理由で Docker を使わず、PostgreSQL を Windows へ直接インストールする方針だった。
>
> **その後、Docker Desktop を前提とする形へ戻した。** ライセンスに関する事実そのものは変わっていないが、利用者が自身の環境で問題ないと判断したため。**判断を消さずに経緯として残す**（前の方針を知らずに「なぜ直接インストールしないのか」と再検討することを防ぐため）。
>
> 撤回にあたり、v1.0 で書いていた「コンテナ実行環境が無いため Testcontainers は使えない」という制約は**解消された**。ただしテスト方針は 7.2 のとおり最小限のまま変えない。

## 8. 将来の拡張：公開する場合に決定すべき事項

MVP は P-2（外部公開しない）を前提とする。将来クラウドへ公開する場合、以下の検討が新たに必要となる。**検討漏れではなく、意図的にスコープ外としている。**

| 分類 | 決定すべきこと |
| --- | --- |
| **認証** | **公開する時点で必須になる。** `users` テーブルの追加、パスワードのソルト付きハッシュ保存、セッション管理、未認証時の制御。`boards` に `user_id` を追加してデータを分離する必要もある |
| 公開範囲 | 第三者の登録を許すか（招待制／登録無効化／ドメイン制限） |
| ホスティング | アプリとDBの配置先、無料枠の制限、月額上限、独自ドメイン、開発用と本番用のDB分離 |
| セキュリティ | HTTPS、Cookie属性（HttpOnly / Secure / SameSite）、CSRF対策、ログイン試行回数の制限、パスワードポリシー、依存パッケージの脆弱性対応 |
| 個人情報 | パスワードリセット（`users` へのメールアドレス列の追加と、メール送信基盤が必要）、退会とデータ削除、プライバシーポリシー |
| 可用性・運用 | バックアップと復旧手順（RPO / RTO）、監視と障害通知、想定稼働時間、ログの保存方針 |
| 前提の見直し | **P-3（PCのみ）が維持できなくなる。** 公開の目的が「どこからでも使う」ことである以上、スマートフォン対応が事実上要求される |
| 非機能要件 | レスポンス目標・同時接続数・データ量を、実測に基づく数値で置き直す |
